# G05 架构设计

> 阶段 2 产出物 · SLA 检查点：组件图 + 部署图 + 接口契约 + ADR

## 一、架构总览

分层架构，依赖单向向下，上层可替换而不影响下层。

```
┌──────────────────────────────────────────────────────────────────┐
│  表现层  web/index.html（零依赖单页）  │  Swagger /docs          │
├──────────────────────────────────────────────────────────────────┤
│  接口层  api/routes/  devices · points · lineage · audit · import │
│          api/deps.py  get_db / get_operator / get_trace_id        │
│          schemas/dto.py  Pydantic 出入参校验                      │
├──────────────────────────────────────────────────────────────────┤
│  服务层  services/point_service.py  改名(带影响面) / 软删 / 版本链 │
│          importers/  validator(YAML规则) · bulk_importer(整批原子) │
│          lineage/impact.py  BFS影响面 / 环检测 / 图导出           │
│          audit/service.py   审计写入口 + 自动埋点                 │
├──────────────────────────────────────────────────────────────────┤
│  模型层  models/  SQLAlchemy 2.0 声明式（7 表）                   │
├──────────────────────────────────────────────────────────────────┤
│  基础设施 core/config(YAML配置中心) · core/db(引擎/PRAGMA)        │
│           core/logging(JSON日志) · core/schema(触发器DDL)         │
├──────────────────────────────────────────────────────────────────┤
│  存储层  SQLite (WAL)  data/db/g05.db                             │
└──────────────────────────────────────────────────────────────────┘
```

### 依赖规则

| 规则 | 说明 |
|---|---|
| 接口层不直接碰 ORM 查询细节 | 复杂逻辑下沉服务层 |
| 服务层不感知 HTTP | 抛领域异常（`PointNotFoundError`），由路由转 HTTP 码 |
| 模型层不含业务判断 | 只描述结构、约束、关系 |
| 配置只从 `core/config` 读 | 禁止在业务代码里写死数字 |

### 外键与级联策略

| 关系 | ondelete | 业务语义 |
|---|---|---|
| `measure_point.device_id → device.id` | **RESTRICT** | 有测点的设备不允许物理删除（资产保护），业务走软删 |
| `record.device_id / point_id` | CASCADE | 设备物理删除时历史记录一并清理 |
| `alarm.device_id / point_id` | CASCADE | 同上 |
| `lineage_edge.upstream_id / downstream_id` | CASCADE | 节点删除时边自动清理 |
| `measure_point.superseded_by → measure_point.id` | SET NULL | 版本链断裂不阻塞删除 |

### 索引设计

| 索引 | 表 | 支撑查询 |
|---|---|---|
| `ix_device_type_status` | device | 按类型+状态筛选列表 |
| `ix_point_device_active` | measure_point | 设备下活跃测点 |
| `ix_point_type_active` | measure_point | 按类型盘点 |
| `ix_record_point_ts` | record | **最左前缀**：按测点查时段 |
| `ix_record_device_ts` | record | 按设备查时段 |
| `ix_alarm_active` | alarm | 未恢复告警 |
| `ix_audit_table_time` | audit_log | 按表+时间倒序查审计 |
| `ix_audit_operator_time` | audit_log | 按人查操作 |

## 三、接口契约（第 1 周冻结）

### 3.1 通用约定

| 项 | 约定 |
|---|---|
| 前缀 | `/api` |
| 操作人 | 请求头 `X-Operator`，缺省 `anonymous` |
| 链路 ID | 请求头 `X-Trace-Id`，缺省自动生成，贯穿审计 |
| 错误格式 | `{"detail": "..."}`，HTTP 码语义化（400/404/409/413/500） |
| 分页 | `page`(≥1) / `size`(1~200)，响应含 `total` |
| 时间 | ISO 8601，UTC |

### 3.2 设备

| 方法 | 路径 | 说明 | 主要错误 |
|---|---|---|---|
| GET | `/api/devices` | 分页查询，支持 `device_type`/`status`/`keyword` | — |
| GET | `/api/devices/{id}` | 详情 | 404 |
| GET | `/api/devices/{id}/points` | 设备下测点 | — |
| POST | `/api/devices` | 新增 | 409 编号重复 |
| PATCH | `/api/devices/{id}` | 更新 | 404 |
| DELETE | `/api/devices/{id}` | 软删 | 404 / **409 仍有活跃测点** |

### 3.3 测点

| 方法 | 路径 | 说明 | 主要错误 |
|---|---|---|---|
| GET | `/api/points` | 分页查询 | — |
| GET | `/api/points/{id}` | 详情 | 404 |
| POST | `/api/points` | 新增 | 400 设备不存在 / 409 编号重复 |
| POST | `/api/points/{id}/rename` | **改名并返回影响面** | 404 / 409 名称未变 |
| DELETE | `/api/points/{id}` | 软删 | 404 |

## 四、关键流程

### 4.1 测点改名流程

```
POST /points/{id}/rename
   │
   ├─1. 加载测点（不存在/已删 → 404）
   ├─2. 名称未变 → 409
   ├─3. ★ 先算影响面（point_code 不变，改名前后结果一致）
   │     impact_of(point_code, downstream) → BFS 逐层 IN 查询
   ├─4. 更新：point_name / version+1 / renamed_from / change_note
   ├─5. 打 _g05_skip_audit 标记，避免自动埋点重复
   ├─6. 显式写 RENAME 审计（含 old/new + reason + operator）
   └─7. commit → 返回影响面
```

### 4.2 批量导入流程

```
POST /import/excel
   │
   ├─1. 校验扩展名 + 大小（≤50MB）
   ├─2. 解析 sheet「设备」「测点」
   │     └─ 超 max_rows(200000) → 拒绝
   ├─3. 构建外键上下文：已存在设备编号 ∪ 本批导入设备编号
   ├─4. RuleEngine 校验
   │     ├─ 计分：完整性40% + 合规性35% + 唯一性25%
   │     └─ 放行 = 分数≥85 且 无结构性错误(required/unique/foreign_key)
   ├─5. 任一 sheet 不通过 → 整批不写，返回打回单（带 Excel 行号）
   └─6. 全部通过 → device bulk_insert → 取 id 映射 → point bulk_insert
                    → 写审计 → commit（异常则 rollback 整批）
```

### 4.3 审计自动埋点

```
SQLAlchemy Session
   │
   ├─ loaded_as_persistent → 拍 _g05_old_snapshot（供 UPDATE 的 old_value）
   └─ before_flush
        ├─ session.new     → INSERT 审计（除非 _g05_skip_audit）
        ├─ session.dirty   → UPDATE 审计（含 old/new 快照）
        └─ session.deleted → DELETE 审计
```

**为什么显式审计优先**：自动埋点只知道"改了什么"，不知道"为什么"。改名、软删等关键操作由服务层显式写 `RENAME`/`SOFT_DELETE` 并附 `reason`，同时打标记跳过自动埋点，避免一条变更产生两条记录。

## 六、架构决策记录

| ADR | 决策 | 理由摘要 |
|---|---|---|
| [ADR-001](adr/ADR-001-orm-and-sqlite.md) | SQLAlchemy 2.0 + SQLite | 声明式约束表达力强；单文件免运维；WAL 满足崩溃恢复 |
| [ADR-002](adr/ADR-002-soft-delete-versioning.md) | 软删 + 版本号，不物理删 | 资产目录历史不可丢；审计需能追到旧值 |
| [ADR-003](adr/ADR-003-audit-immutability.md) | 应用层 + 数据库触发器双保险 | 单靠应用层可被绕过；触发器连 DBA 也改不了 |
| [ADR-004](adr/ADR-004-lineage-bfs.md) | 逐层 BFS 而非递归 SQL | 深度可控、易检测环、每层一条 IN 查询无 N+1 |

## 七、扩展点

| 方向 | 接入方式 |
|---|---|
| 换 PostgreSQL | 改 `config/database.yaml` 的 URL；`PRAGMA` 钩子按方言跳过 |

| 分区归档 | `config/database.yaml` 的 `archive` 段已预留 |
