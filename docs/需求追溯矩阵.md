## 一、这张表怎么读

每条需求标注三种状态之一，**不写"已完成"这种含糊话**：

| 标注 | 含义 | 判据 |
|---|---|---|
| ✅ **已验收** | 代码在 `main` 上，且**当场跑过验证命令** | 验证命令能复现出预期结果 |
| ⏳ **待合入** | 代码已写完、在某人分支上，PR 未合 | PR 已开且内容已 review 通过 |
| ❌ **未开始** | 还没有代码 | — |

> **为什么这么严**：验收标准写的是"每个结论都能指向仓库里的具体文件或命令"。
> 只有在 `main` 上跑通才叫验收 —— 在别人分支上跑通只能叫"待合入"。
> 现场答辩被要求复现时，只有 ✅ 的能当场演示。

**当前基线**：`main` = `1b486dd`（2026-11-11）。M4 各角色 PR 已全部合入：
**#57 C3 审计** · **#61 C2 报告导出** · **#62 C4 CRUD+前端+错误码** · **#64 C1 批量导入器** · **#65 A 触发器自检** · **#66/#67 C6 文档** · **#68 A 联调修复**。
每个 PR 均走完整闭环：分支 → CI 绿 → REST 合并 → 关联 issue 关闭。

### 关于"功能层基线"的重要说明（2026-11-05）

项目初始提交 `9b10869`（作者 G05 Team，10-23）里**已包含全套功能代码**。
经核对：9 个分发包里的文件与 `origin/master` 上的实现 md5 基本一致 ——
**发包实质是把一份预先写好的参考实现切给各人当起点**，不是从零实现。

因此本次集成采取的路径是：

> **先把这套参考实现合进 main 作为基线**（main 立刻可演示、可答辩），
> **各人再在基线上重做与改进**（各人的 PR = "在现有实现上的改进"，贡献度依然清晰）。

所以本表里的 ✅ 指的是"**功能可用且已实测通过**"，不等于"某人独立从零实现"。
答辩时要说清这个区别 —— 参见 `docs/答辩材料.md` 的贡献度章节。
