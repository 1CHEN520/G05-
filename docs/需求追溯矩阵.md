## 一、这张表怎么读

每条需求标注三种状态之一，**不写"已完成"这种含糊话**：

| 标注 | 含义 | 判据 |
|---|---|---|
| ✅ **已验收** | 代码在 `main` 上，且**当场跑过验证命令** | 验证命令能复现出预期结果 |
| ⏳ **待合入** | 代码已写完、在某人分支上，PR 未合 | PR 已开且内容已 review 通过 |
| ❌ **未开始** | 还没有代码 | — |

> **为什么这么严**：验收标准写的是"每个结论都能指向仓库里的具体文件或命令"。
> 只有在 `main` 上跑通才叫验收 —— 在别人分支上跑通只能叫"待合入"。
> 现场答辩被要求复现时，只有 ✅ 的能当场演示。

**当前基线**：`main` = `10b4814`（#43 B1 ORM 已合入，#44 契约 DTO 与 preflight 修复已合入，#45 归属与生成脚本已合入）

## 七、维护规则

1. **每合一个 PR 就在本表回填状态**，并注明验证命令与实测结果。
2. 状态只写 ✅/⏳/❌ 三种，不写百分比 —— 答辩现场问"到底行不行"，要能一句话回答。
3. **在别人分支上跑通只能叫 ⏳ 待合入**；只有 `main` 上复现才算 ✅。
4. 本表由 A 维护，改动需与对应 PR 的评审意见一致。
