## 二、对应 GB/T 8566 软件生存周期过程

GB/T 8566（等同 ISO/IEC 12207）把软件生存周期划分为**基本过程 / 支持过程 / 组织过程**。本项目的落地对照：

### 2.1 基本过程

| GB/T 8566 过程 | 本项目活动 | 证据 |
|---|---|---|
| **获取过程** | 选题、可行性分析、组队分工 | `docs/00` 第一章 |
| **供应过程** | 交付 Git 仓库 + 现场克隆演示 | `README.md` 快速开始 |
| **开发过程** | | |
| ├ 需求分析 | 用户故事 + 非功能需求 + 边界界定（做什么/不做什么） | `docs/01` 第一、二、三章 |
| ├ 架构设计 | 分层架构 + ER 模型 + 接口契约冻结 | `docs/02` 第一~四章 |
| ├ 详细设计 | ADR 记录 4 个关键决策的备选方案对比 | `docs/adr/` |
| ├ 编码 | 分层实现，依赖单向 | `src/g05/` |
| ├ 集成 | 接口层组装服务层，`main.py` 统一注册路由 | `src/g05/main.py` |
| └ 测试 | 单元测试 + 故障注入 + 性能测试 | `tests/`、`scripts/fault_inject.py` |
| **运行过程** | 一键启动、健康检查、指标接口 | `run.bat`、`/healthz`、`/metrics` |
| **维护过程** | 配置外置（改配置不改代码）+ 审计追溯变更 | `config/*.yaml`、`/api/audit` |

### 2.2 支持过程

| 过程 | 本项目活动 | 证据 |
|---|---|---|
| **文档编制** | 需求/架构/ADR/运行手册/演示脚本/踩坑记录 六类文档 | `docs/` |
| **配置管理** | Git 分支策略 + 依赖版本锁定 + `.gitignore` 排除数据与日志 | `requirements.txt`、`.gitignore` |
| **质量保证** | pytest 46 用例 + 评分口径文档 + 代码分层审查 | `tests/`、`docs/02` |
| **验证** | 硬指标实测（导入<30s / 血缘<1s / 孤儿被拒 / 审计可回溯） | README 第三节 |
| **确认** | 用户故事逐条对照验收条件 | `docs/01` 第二、六章 |
| **联合评审** | 架构走查、交叉抽测、答辩 | 里程碑 M1/M4/M5 |
| **审计** | **本项目核心功能**：append-only 审计 + 触发器防篡改 | `models/audit_log.py`、`core/schema.py` |
| **问题解决** | 踩坑记录 8 条（问题→根因→解法→预防） | `docs/踩坑记录.md` |

## 三、对应 TOGAF ADM 八阶段

TOGAF ADM（Architecture Development Method）是企业架构开发方法，八个阶段 A~H。本项目虽小，但产物可完整映射：

| ADM 阶段 | 名称 | 本项目产物 | 位置 |
|---|---|---|---|
| **预备阶段** | Preliminary | 技术选型基线（Python/SQLite/SQLAlchemy）、分层架构原则 | `docs/adr/ADR-001` |
| **A** | 架构愿景 | 一句话定位 + 干系人 + 边界（做什么/不做什么）+ 开题四问 | `README.md`、`docs/01` §1 |
| **B** | 业务架构 | 12 条用户故事、验收条件、数据质量要求 | `docs/01` §2、§4 |
| **C** | 信息系统架构 | | |
| ├ 数据架构 | ER 图、7 张表、外键与级联策略、索引设计 | `docs/02` §2 |
| └ 应用架构 | 分层组件图、接口契约（6 组 20 个端点） | `docs/02` §1、§3 |
| **D** | 技术架构 | 部署图、运行参数、PRAGMA 配置、日志格式 | `docs/02` §5 |
| **E** | 机会与解决方案 | ADR 四篇（每个决策列备选方案 + 理由 + 后果） | `docs/adr/` |
| **F** | 迁移规划 | 里程碑 M1~M5、甘特图、第 1 周逐日计划 | `docs/00` §4、§11 |
| **G** | 实施治理 | 接口第 1 周冻结、变更需审批、pytest 全绿门禁 | `docs/00` §4.3 |
| **H** | 架构变更管理 | 配置外置（变更不改代码）+ 审计（变更可追溯）+ ADR 记录决策演进 | `config/`、`/api/audit` |

### 3.1 TOGAF 架构内容框架（Architecture Content Framework）对照

| 内容类型 | 本项目 |
|---|---|
| **架构原则** | 三条铁律：可观测 / 可恢复 / 配置外置 |
| **架构视图** | 组件图（应用）、ER 图（数据）、部署图（技术） |
| **架构交付物** | 需求规格、架构设计、ADR、运行手册 |
| **架构构建块（ABB）** | 资产建模、血缘追踪、审计、质量门禁、批量导入 |
| **解决方案构建块（SBB）** | SQLAlchemy ORM、SQLite WAL、FastAPI、BFS 算法、YAML 规则引擎 |

### 3.2 架构治理（Architecture Governance）

| 治理点 | 机制 | 证据 |
|---|---|---|
| 接口稳定性 | 第 1 周冻结，变更需 A 审批 | `docs/00` §11 |
| 代码质量 | pytest 全绿才可合并 | 46 passed |
| 配置合规 | 禁止代码硬编码参数 | 全部参数在 `config/*.yaml` |
| 数据合规 | 审计 append-only，不可改删 | 数据库触发器 |
| 决策留痕 | 关键决策写 ADR，含备选方案与后果 | `docs/adr/` 4 篇 |

## 四、三条铁律的落地证据

| 铁律 | 含义 | 落地 | 可验证 |
|---|---|---|---|
| **可观测** | 出问题能定位 | 结构化 JSON 日志（含 `trace_id`）；慢查询 >200ms 打 WARN；请求耗时写响应头 `X-Elapsed-Ms` | `logs/app.jsonl`、`core/logging.py`、`core/db.py` |
| **可恢复** | 崩了能自愈 | WAL + 事务原子；审计 append-only；启动自动建表装触发器 | `fault_inject.py --case kill` |
| **配置外置** | 改配置不改代码 | 4 个 YAML 文件承载全部参数：端口、导入上限、校验规则、评分权重、连接池、日志 | `config/` |
