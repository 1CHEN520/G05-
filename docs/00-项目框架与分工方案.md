## 一、项目定位与可行性分析

### 1.1 场景背景

重庆两江智造集团12类设备的台账散落在Excel中，测点改名后无人知道影响哪些报表。本项目交付一个**带血缘追踪的设备资产目录系统**，实现设备-测点-记录-告警的统一管理和变更可追溯。

### 1.2 可行性分析

| 维度 | 评估 | 说明 |
|------|------|------|
| 技术可行性 | ✅ 高 | SQLAlchemy 2.0 声明式 ORM 成熟稳定；SQLite 无需独立部署；Python 生态完整覆盖需求 |
| 人力可行性 | ✅ 可行 | 9人满编，L2等级要求7-8人，冗余1人可投入测试加固 |
| 时间可行性 | ⚠️ 紧 | 第5周选题→第8周验收，共3周开发+1周答辩准备，需并行推进 |
| 数据可行性 | ✅ 可行 | 12类设备+测点可构造仿真数据集，万行导入验收可复现 |
| 风险 | 中 | 3周周期紧张；血缘查询性能需提前压测；批量导入边界处理需充分测试 |

### 1.3 开题四问预答（README首页必答）

| 问题 | 回答策略 |
|------|----------|
| 断电重启会怎样？ | SQLite WAL模式 + 事务原子写入，重启后数据完整无缺口；审计表 append-only，重启不丢审计记录 |
| 并发上来扛得住吗？ | SQLAlchemy 连接池 + 批量导入bulk插入；万行导入<30秒硬指标；查询走索引 |
| 出问题能查到人/根因吗？ | 审计表记录 谁/何时/改了什么；血缘查询定位变更影响面；日志分级可追溯 |
| 换台机器跑得起来吗？ | 一键 `conda activate pp03 && python main.py`；依赖锁定 requirements.txt；配置外置 YAML |
| 怎么对应软件工程流程及国标和TOGAF？ | 需求→架构→编码→测试→运维全流程覆盖；对标GB/T 8566软件生存周期；TOGAF ADM阶段映射见架构设计章节 |

**分组原则：**
- **A（1人）**：全局视角，不陷入具体编码，专注于架构决策、接口管理、进度风控、集成验收。答辩主讲。

- **C（6人）**：按功能模块两两配对，形成3个执行对子：
  - C1/C2 → 导入校验对（对应B1 ORM指导）
  - C3/C4 → 审计CRUD对（对应B2血缘指导）
  - C5/C6 → 测试文档对（横切所有模块）
