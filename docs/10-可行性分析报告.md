## 一、项目概述

**项目名称**：工业设备台账与测点资产目录系统（G05）

**拟解决的问题**：工厂场景下设备与测点的台账目前依赖 Excel 手工维护——改名无影响面预警、改动无痕迹、坏数据无防线。本项目用 Python 构建一个可批量导入、自动追溯、扛得住故障的设备台账与测点血缘系统。

**目标规模**：200 台设备 / 600 测点级数据量，单机部署，3-9 人课程团队在 8 周内交付。

## 二、可行性分析

### 2.1 技术可行性

| 考察项 | 分析 | 结论 |
|---|---|---|
| 语言与框架 | Python 3.12 + FastAPI：路由容错注册、自动 OpenAPI 文档、Pydantic 契约校验均为成熟能力，无自研框架风险 | ✅ 成熟 |
| 数据存储 | SQLite 单文件：零运维成本，WAL 模式支持读写并发；对外键、触发器（审计 append-only）支持完整。规模上限（单写者）对单机台账场景够用，并在设计中预留 L3 迁移 PostgreSQL 的路径（ADR-001） | ✅ 够用且留有升级路径 |
| 核心算法 | 血缘影响面 = 有向图 BFS，O(V+E)，200 节点毫秒级（后实测 4.59ms）；改名采用版本链（superseded_by）避免重建血缘图（ADR-002） | ✅ 已验证 |
| 性能目标 | 万行导入 <30s：bulk_insert_mappings + 分批 flush，量大时风险可控（后实测 1.14s） | ✅ 已验证 |
| 测试工具链 | pytest + coverage + ruff + pylint + 自研 fault_inject，全部开源且文档充分 | ✅ 成熟 |

**结论：技术可行**。验证结果：M2-M4 全部按此技术栈交付，无技术性返工。

### 2.2 经济可行性

| 成本项 | 分析 | 结论 |
|---|---|---|
| 软件许可 | FastAPI / SQLAlchemy / SQLite / pytest / ruff / pylint 全部开源免费 | ✅ 零许可成本 |
| 硬件 | 开发与部署均在普通 PC（一台 8GB+ 内存笔记本即可），无云资源采购 | ✅ 零硬件成本 |
| 人力 | 9 人课程团队，工作量为学习成本，无外包 | ✅ 可承受 |

**结论：经济可行**。验证结果：项目全程零采购。

### 2.3 操作可行性

| 考察项 | 分析 | 结论 |
|---|---|---|
| 部署门槛 | `pip install -e .` → `python -m g05 preflight` → `python -m g05 serve` 三条命令完成启动；环境自检输出 JSON 供自动判定 | ✅ 一键可启动 |
| 使用门槛 | Web 控制台四页（设备/测点/审计/导入），业务方无需培训；数据入口为带校验的 Excel 模板（模板说明见 docs/05） | ✅ 业务方可直接使用 |
| 维护门槛 | 运维巡检清单 8 项 + runbook 故障处置预案三段式；11-13 由非运维同学独立演练通过（issue #35） | ✅ 新人可上手 |

**结论：操作可行**。验证结果：部署、巡检、恢复三条路径均已由「没参与开发的人」独立走通。

### 2.4 进度可行性（社会/时间因素）

| 考察项 | 分析 | 结论 |
|---|---|---|
| 人员与周期 | 9 人满编（组长 + 内核 2 + 开发 4 + 测试 1 + 文档 1），8 周 4 个里程碑 | ✅ 满编分工 |

**结论：进度可行**。验证结果：M4 于 2026-11-13 结项，39 个 issue 全部关闭。

### 2.5 法律与合规可行性

| 考察项 | 分析 | 结论 |
|---|---|---|
| 许可与引用 | 全部依赖为开源组件，无侵权引用；文档遵循 GB/T 8566 / 9385 / 15532 / 8567 对应章节编制 | ✅ 合规 |
| 数据合规 | 系统不含真实工业数据（全部固定种子合成数据），无个人信息与涉密内容，无出域风险 | ✅ 合规 |
| 密码安全 | 无认证模块（设计取舍，NFR-08），无密码存储面即无明文风险；L3 引入用户体系时按 PBKDF2 哈希 | ✅ 合规 |

**结论：合规可行**。

## 三、结论

技术、经济、操作、进度、合规五个维度全部可行。项目于 2026-10-19 立项启动，上述每一项结论均已在 M1-M4 实施中得到验证：无一维度在中途推翻立项假设。

## 四、可行性分析中曾识别的三大风险及实际处置

| 风险 | 立项时的判断 | 实际处置与结果 |
|---|---|---|
| 团队开工风险（发包≠开工） | 高：课程团队历史上常见发包后无人动手 | AGENTS.md 固化纪律 + 逐人盯 issue；最终 9/9 人人人有 commit |
| 性能风险（万行导入超时） | 中：ORM 逐行插入是常见反模式 | 单事务 + 分批 flush + bulk_insert_mappings；实测 1.14s |
| 数据可信风险（性能/验收数字失真） | 中：基线脚本可能测错对象 | 建立对账与 EXPLAIN 实测脚本；主动废弃过 0.18ms 假数字（详见踩坑记录） |
