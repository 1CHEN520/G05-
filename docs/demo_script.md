## 一、问题（1.5 分钟）

> **【A-01 组长】**

"各位老师好，我们组选的是 **G05 设备台账与测点资产目录**。

先讲我们解决什么问题。方总监的原话是：**12 类设备的台账散在 Excel 里，测点改名没人知道影响哪些报表。**

这句话里其实藏了三个痛点：

**第一，台账不可信。** 12 个 Excel 文件，谁最后改的不知道，改了什么不知道。出了事故查不到人。

**第二，改名是盲改。** 工艺员把「轴承温度」改成「轴承温度(驱动端)」，他不知道 OEE 日报、质量周报、健康度评分全都在读这个测点。改完报表数字对不上，追三天才发现是上游改了字段。

**第三，脏数据进门没人拦。** 设备编号写成小写、测点挂到不存在的设备上，这些错误一旦入库，后面所有报表都是错的。

所以我们要交付的不是一个 CRUD 系统，而是**一个带血缘追踪、变更可审计的资产目录**。

这三个痛点，对应我们的三条设计主线：**血缘、审计、门禁**。"

---

## 二、方案（2.5 分钟）

> **【A-01 组长】讲架构，【B-02】讲血缘**

### 2.1 整体架构（1 分钟）

> 切到 `docs/02-架构设计.md` 的架构图，或口述

"技术栈是 **Python + FastAPI + SQLAlchemy 2.0 + SQLite**。

为什么选 SQLite？因为课程环境不允许独立数据库服务。但我们没有把它当玩具用：

- 开 `WAL` 模式，崩溃可恢复
- 开 `foreign_keys=ON`（SQLite 默认是关的，这是个大坑）
- 连接池 + `busy_timeout` 扛并发

分层是标准的四层：**接口层 → 服务层 → 模型层 → 存储层**，依赖单向向下。

三条铁律我们落实了：
- **可观测**：结构化 JSON 日志，每条带 trace_id
- **可恢复**：WAL + 事务原子写入
- **配置外置**：所有参数在 4 个 YAML 里，改配置不改代码"

### 2.2 血缘怎么做的（1 分钟）

> **【B-02 血缘负责人】**

"血缘这块我讲一下核心思路。

我们建了两张表：`lineage_node` 存节点（测点/数据集/报表/任务/接口），`lineage_edge` 存依赖边。

**影响面查询就是从测点节点出发，向下游做 BFS。**

关键设计有三点：

**第一，逐层 BFS，不是递归 SQL。** 每层一条 `IN` 查询，深度通常不超过 3 层。实测单点下游 11 个节点，**6 毫秒**。

**第二，记录完整路径。** 返回的不是一堆节点，而是 `FAN0001_VIB → DS_CLEAN_TS → RPT_OEE_DAILY` 这样的链路。工艺员一看就知道"我这个测点是通过清洗宽表影响到 OEE 日报的"。

**第三，环检测内建。** BFS 的 `visited` 集合命中就是环，不用额外算法。数据库层还有触发器拦自环边。

这个决策我们写了 ADR-004，里面列了 4 个备选方案的对比。"

### 2.3 审计怎么保证改不了（0.5 分钟）

> **【C-03 审计负责人】**

"审计这块，评分标准写了红线：**审计可改 = 该维度 0 分**。

所以我们是**双保险**：

- 应用层：`AuditService` 只暴露 `record()` 写入，**根本没有** update/delete 方法
- 数据库层：两个触发器，`BEFORE UPDATE` 和 `BEFORE DELETE` 直接 `RAISE(ABORT)`

第二道是关键 —— **即使拿到数据库文件，用 sqlite3 命令行也改不了**。

这个我等下现场演示。"

| 顺序 | 文件 | 讲解人 | 讲什么 |
|---|---|---|---|

| 6 | `src/g05/core/schema.py` | C-03 | 触发器 DDL 集中定义 |

### 3.2 关键代码片段（1 分钟）

**B-01 讲模型**

"测点表有三个字段值得说：

```python
is_deleted: Mapped[bool]        # 软删，不物理删
version: Mapped[int]            # 版本号，每次变更 +1
renamed_from: Mapped[str|None]  # 保留旧名
```

改名不删除 —— 因为资产目录的历史本身就是资产。审计的 `old_value` 要能指向真实存在过的数据。"

**C-02 讲规则配置**

"校验规则全在 YAML 里：

```yaml
device_code:
  required: true
  unique: true
  regex: "^[A-Z]{2,4}-\\d{3,6}$"
```

工艺员要加个新设备类型，改一行枚举就行，**不用找我们改代码**。这是工业级和 demo 的分水岭。"

**C-01 讲导入**

"导入是整批原子的：

```
解析 → 校验 → 有错？整批不写，出打回单
              ↓ 无错
         bulk_insert 分片提交 → 任一分片失败 → 全部 rollback
```

打回单每条问题标注 **Excel 实际行号**，不是索引号。用户拿着单子直接去第 3 行改。"

### 4.2 故障注入（2 分钟）—— **重点**

> 切到终端

```bash
python scripts/fault_inject.py --all
```

**逐个念结果**

```
[1/5] 孤儿记录注入
  ✓ 插入被拒绝：IntegrityError
    FOREIGN KEY constraint failed
```

"测点挂到不存在的设备上，数据库直接拒绝。这不是我们代码判断的，是外键约束。"

```
[2/5] 审计篡改注入
  ✓ UPDATE 被触发器拒绝
    audit_log is append-only: UPDATE forbidden
  ✓ DELETE 被触发器拒绝
    audit_log is append-only: DELETE forbidden
```

"**这就是刚才说的第二道防线。** 绕过应用层，直接对数据库发 SQL，一样改不了。"

```
[3/5] 脏数据导入
  ✓ 整批被打回，设备数未变（60 -> 60）
    [device] 共 2 行，通过 1，问题 1 行，得分 87.2/85.0 -> 打回(结构性错误)
    | 3 | device_code | regex | device_code 格式不合法: fan-9002 |
```

"注意这里：**得分 87.2 高于阈值 85，但依然被打回**。因为必填缺失、编号重复、外键悬空是结构性错误，一票否决 —— 不能靠高分抵消。"

```
[4/5] kill -9 强杀恢复
  ✓ 强杀后完整性检查 = ok
  ✓ 已落盘记录 819 条，重启可读
```

"子进程连续写库，1.8 秒时 `SIGKILL` 强杀 —— 相当于直接拔电源。重启后 `integrity_check = ok`，已提交的 819 条一条不少。这是 WAL 的功劳。"

```
[5/5] 并发写入压测
  ✓ 8 线程 × 40 条 = 320，实际入库 320，耗时 0.19s
  ✓ 无 database is locked
```

"8 个线程同时写，320 条全部入库，0 报错。"

## 六、预设问答（Q&A 准备）

### Q1：为什么用 SQLite？生产环境能用吗？

**答**：
"课程环境不允许独立数据库服务，这是约束。但我们的架构没有绑死 SQLite：

- ORM 层隔离方言，换 PostgreSQL 只需改 `config/database.yaml` 的连接串
- `PRAGMA` 钩子会按方言跳过

SQLite 的真实限制是**单写者**，高并发写会串行。我们做了三件事缓解：

1. WAL 模式允许读写并发
2. `busy_timeout=5000` 避免锁冲突
3. 批量导入用 `bulk_insert` 减少事务次数

实测 8 线程并发写入 0 冲突。但如果是几百 QPS 的写入场景，必须迁 PostgreSQL —— 这一点我们在 ADR-001 的"后果"里明确写了。"

### Q2：血缘的边是怎么来的？要人工维护吗？

**答**：
"目前是显式注册：`POST /api/lineage/edges`。

这是**已知限制**，我们在需求文档里写明了。工业上的做法是埋点 SDK —— 任务执行时自动上报输入输出。G17 数据血缘追踪系统就是这个方向。

我们的模型已经为 SDK 预留了：`lineage_edge` 有 `field_name`（字段级血缘）和 `relation`（read/join/aggregate），SDK 接进来只需调用 `register_edge()`。"

### Q3：如果两个人同时改同一个测点会怎样？

**答**：
"会串行执行，后提交的覆盖前者，版本号递增两次。

这是**乐观并发的简化版**。严格做法是加 `version` 做 CAS：`UPDATE ... WHERE id=? AND version=?`，版本不匹配就报冲突。

我们目前没做，因为：

1. 测点改名是低频操作
2. 审计表记录了两次变更，能查出来是谁后改的

如果要做，改动很小 —— 在 `rename_point` 的 update 加 `WHERE version = old_version` 即可。这是明确的演进点。"

### Q4：审计表会不会无限膨胀？

**答**：
"会，而且我们**故意**不清理 —— 合规要求。

缓解方式：

1. `config/database.yaml` 的 `archive` 段预留了归档配置，按年归档到只读文件
2. 审计表只建了两个必要索引，避免写放大
3. 十万级/年的量级，SQLite 完全扛得住（千万行以内性能可接受）

如果真要清理，正确做法是归档后**新建表 + 迁移**，而不是 DELETE —— 因为触发器禁止 DELETE。"

### Q5：你们的测试真的覆盖了边界吗？

**答**：
"举三个例子：

**第一，结构性错误不能被高分抵消。** `test_fatal_rule_cannot_be_offset_by_score` 把阈值降到 1 分，必填缺失的数据依然被打回。

**第二，坏行号是 Excel 行号不是索引。** `test_bad_row_numbers_are_excel_rows` 断言第二条数据报 `row_no=3`（表头占第 1 行）。

**第三，性能是断言不是口号。** `test_import_10k_rows_under_30s` 和 `test_impact_query_performance` 直接断言耗时，CI 跑不过就合不了。"

### Q6：如果评委现在删掉一个文件，系统还能跑吗？

**答**：
"看删哪个：

- 删 `data/db/g05.db` → `init_db.py` 重建，`seed_data.py` 灌数据，能跑
- 删 `config/rules.yaml` → 校验引擎抛 `KeyError` 提示"rules.yaml 未定义 sheet"，不会静默失败
- 删 `web/index.html` → 首页降级为纯文本链接页，API 不受影响
- 删 `src/g05/main.py` → 跑不起来，这是入口

我们在设计上尽量让"缺东西"变成**明确报错**而不是**静默降级** —— 因为静默降级在生产上更危险。"
