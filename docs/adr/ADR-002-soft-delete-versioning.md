# ADR-002 软删除 + 版本号，不做物理删除

- **状态**：已接受
- **日期**：2026-10（第 5 周）
- **决策者**：A 组长、B1 建模负责人

## 背景

资产目录的"删除"与普通业务数据不同：设备/测点的历史变更本身就是资产，需要长期可查。同时需求明确要求「改名不删除（软删/版本）」、审计要能回溯任一变更。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 软删（`is_deleted`）+ 版本号（`version`）** | 行保留，历史可查；外键仍指向真实行；审计 old_value 有意义 | 所有查询都要带 `is_deleted=False`，易漏 |
| B. 物理删除 | 表干净、查询简单 | 历史丢失；审计记录变成悬空引用；外键 RESTRICT 会阻塞删除 |
| C. 双表（主表 + 历史表） | 主表精简，历史表可分区 | 写操作要同步两表，事务复杂；查询历史需 union |
| D. 时态表（valid_from/valid_to） | 支持"任意时点快照"查询 | 模型复杂度高；SQLite 无原生支持，需手写大量区间逻辑 |

## 决策

采用 **A**，并在关键字段上加辅助：

| 字段 | 作用 |
|---|---|
| `is_deleted` | 软删标记，带索引 |
| `version` | 每次变更 +1，用于展示"这是第几版" |
| `deleted_at` | 删除时间，支撑保留期策略 |
| `renamed_from` | 改名场景保留旧名，血缘查询沿版本链回溯 |
| `change_note` | 变更原因，配合审计的 `reason` |

**改名不产生新行**：只更新 `point_name`，`version+1`，`renamed_from` 存旧名。因为 `point_code` 不变，血缘边无需重连 —— 这是选择"改 name 不改 code"的关键收益。

## 后果

**正面**
- 历史零丢失，审计 `old_value` 永远指向真实存在过的数据
- 外键约束始终有效（不会因为删除导致悬空引用）
- 可回答"这个测点以前叫什么"这类追溯问题

**负面**
- 查询必须显式过滤 `is_deleted=False`，漏写会返回已删数据
- 表会随时间膨胀（资产量级小，可接受）
- 唯一约束需注意：软删后重建同名记录会撞唯一键

**缓解措施**
- 查询封装在服务层（`list_points` / `list_devices`），默认过滤已删；需要含删数据时显式传 `include_deleted=True`
- 唯一约束加在业务键上，软删不释放业务键 —— 明确"编号一旦使用不可复用"，符合工业资产编码规范
- 设备物理删除用 `RESTRICT` 拦住（有测点就不许删），业务层一律走软删

## 验证

```bash
pytest tests/test_models.py -k "soft_delete or version" -q
pytest tests/test_models.py -k "physical_delete_device_with_points_blocked" -q
```
