## 一、一页架构图

```
┌─────────────────────────────────────────────────────────────────────────┐
│  表现层    web/index.html（零依赖单页）    Swagger /docs                 │
├─────────────────────────────────────────────────────────────────────────┤
│  接口层    api/routes/  devices · points · lineage · audit · imports     │
│            api/deps.py   get_db / get_operator / get_trace_id            │
│            schemas/dto.py   Pydantic 出入参校验（契约冻结点）            │
│            schemas/errors.py  24 个错误码 + ApiError（契约冻结点）       │
├─────────────────────────────────────────────────────────────────────────┤
│  服务层    services/point_service.py   改名(带影响面) / 软删 / 版本链     │
│            importers/validator.py      YAML 规则引擎（六类）             │
│            importers/bulk_importer.py  批量入库 + 整批原子回滚           │
│            lineage/impact.py           BFS 影响面 / 环检测 / 图导出      │
│            audit/service.py            审计写入口 + SQLAlchemy 自动埋点 │
├─────────────────────────────────────────────────────────────────────────┤
│  模型层    models/  SQLAlchemy 2.0 声明式（7 表 + 软删版本机制）          │
│            base.py  UTCDateTime · alive_filter · version_id_col 乐观锁   │
├─────────────────────────────────────────────────────────────────────────┤
│  基础设施  core/config.py  YAML 配置中心 + G05_XXX__YYY 环境变量覆盖      │
│            core/db.py     引擎 / PRAGMA / 200ms 慢查询钩子               │
│            core/logging.py  JSON Lines 日志 + trace_id 贯穿              │
│            core/schema.py   触发器 DDL（只对已存在的表装）                │
├─────────────────────────────────────────────────────────────────────────┤
│  存储层    SQLite（WAL 模式）  data/db/g05.db                            │
└─────────────────────────────────────────────────────────────────────────┘
```

**四个设计决策，各有硬约束兜着：**

| 决策 | 为什么这么定 | 硬约束在哪 |
|---|---|---|
| 依赖单向向下，上层可替换 | 换前端不动后端，换存储不动服务层 | `docs/02-架构设计.md` 依赖规则表 |
| 服务层抛领域异常，路由转 HTTP 码 | 服务层不感知 HTTP，才能被脚本和测试直接调用 | `services/point_service.py` |
| 配置只从 `core/config` 读 | 禁止业务代码写死数字，改阈值不改代码 | `core/config.py` + `config/*.yaml` |
| 契约冻结在 `schemas/` | DTO 与错误码是公共边界，改动必须走评审 | `schemas/dto.py`、`schemas/errors.py` |

**🟢 现场复现**：

```bash
python -m g05 preflight    # 一条命令证明"环境装对了"
# 看契约长什么样：
python -c "from g05.schemas.dto import ImpactOut, GraphOut; print(ImpactOut.model_fields.keys())"
python -c "from g05.schemas.errors import CODES; print(len(CODES), '个错误码')"
```

## 三、三个数字的前后对比

### 3.1 万行导入耗时

| | 改造前 | 改造后 | 目标 | 结论 |
|---|---|---|---|---|
| 导入方式 | 人工在 Excel 里改，改完靠人核对 | 批量导入 + 规则校验 + 整批原子 | — | — |
| 万行导入耗时 | **无法测量**（没有导入功能） | 🟡 C5 基线实测：**20 设备×3 测点 = 16.37ms**（中位数，5 次） | <30s | 大幅达标 |
| 错误处理 | 改错了不知道，改到第 800 行才发现 | 整批回滚，零脏数据入库 | 零写入 | ✅ |

**为什么现在给的是 16.37ms 而不是万行**：因为 C5 的基线脚本在 C1 的导入器合入前，
用的是 20×3 的小样本 —— 这个数字**不能**直接回答"万行 <30s"。
诚实做法是等 C1 合入后由 C5 跑 10000 行真实样本回填。
（这是 `docs/需求追溯矩阵.md` 遗留清单第 7 条，我不打算用一个漂亮但不对题的数字糊弄过去。）

**🟢 现场复现**（C5 合入后）：`python scripts/bench.py --devices 2000 --points-per-device 5`

### 3.2 血缘查询耗时

| | 改造前 | 改造后 | 目标 | 结论 |
|---|---|---|---|---|
| 查"改这个测点影响谁" | **靠翻 Excel 和问人**，平均半天 | BFS 自动算影响面 | — | — |
| 影响面查询耗时 | 无法测量 | 🟡 **0.18ms**（中位数；min 0.16 / max 5.03） | <1s | 达标，余量 5000 倍 |
| 图导出 | 无 | `total/returned/truncated` 三字段，前端不再把前 N 个说成"全图" | — | ✅ |

**关键不只是快，是"诚实"**：B2 实现了我 11-01 裁定的截断语义 ——

`truncated_by` 说明被谁截断，**不许静默丢弃节点**。
`docs/review/B2-A-contract-decisions.md` 记了裁定的全过程。

**🟢 现场复现**：B2 合入后 `GET /api/lineage/impact?node_type=point&node_key=P_A&direction=downstream`

## 五、六个追问的备答

> 评委最可能问的六个问题，每个都能指到具体文件。

**Q1：凭什么说"改一个测点能知道影响谁"？**
→ `src/g05/lineage/impact.py` 的 BFS 遍历 + 环检测；
契约在 `schemas/dto.py` 的 `ImpactOut`（五字段截断语义）；
裁定过程在 `docs/review/B2-A-contract-decisions.md`。
实测 0.18ms（`reports/bench-baseline.json`）。

**Q2：审计真改不了吗？数据库管理员直接 UPDATE 不就改了？**
→ 改不了。`core/schema.py` 装了两个 SQLite 触发器
（`trg_audit_no_update` / `trg_audit_no_delete`），直接 `RAISE(ABORT)`，
**绕过应用层也改不了**。这是 C3 的活，代码在 `feat/c3-audit`。
C5 的 `fault_inject.py --case tamper` 就是专门验证这个的。

**Q3：性能数字怎么测的？会不会是自己编的？**
→ 脚本在 `scripts/bench.py`，机器可读结果在 `reports/bench-baseline.json`，
报告在 `reports/性能基线报告.md`。**5 次取中位数，同时记录 min/max，写清数据量。**
现场可以重跑。C5 特意说明"导入用独立临时库测"—— 否则第 2 次跑测到的是重复导入，
不是首次导入，性能数字会好看但是假的。

**Q4：9 个人怎么协作的？会不会有人划水？**
→ 分工在 `collab/roles.yaml`（自动生成 `collab/分工文件清单.md`），
一个文件只有一个主人，`make_role_bundles.py --check` 保证没有无主文件。
每个 PR 有模板强制自证。**贡献表我如实列了 5 个人的 0 提交** —— 见 4.2。

**Q5：这东西换个环境还能跑吗？**
→ 能。配置全在 `config/*.yaml`，支持 `G05_SERVER__PORT=9000` 覆盖；
存储是单文件 SQLite（WAL）；依赖只有 `requirements.txt`。
`python -m g05 preflight` 一条命令自检环境，**新人从零到跑起来 ≤30 分钟**。

**Q6：现在到底完成到什么程度？**
→ 逐条需求状态在 `docs/需求追溯矩阵.md`：

   我在干净环境实测是 `false` —— 查下来是他本地有残留的旧数据库。

### 做错的

1. **preflight 有两个 bug，是我自己写的**。①只建表不装触发器 —— 干净环境必然假红，
   大家看到的"绿"是靠工作目录残留的旧库撑着。②`audit_log` 未合入时把中间态判死。
   **教训：自检工具自己需要被测试。** 现在 `cli.py` 的行为有回归测试守着。
2. **生成脚本在 Windows 上写 CRLF**。`collab/issues.md` 一度显示 1766 行变更，
   真实差异只有几行 —— 污染了所有人的 review。**教训：工具链的问题会变成团队的摩擦。**
   已根治（统一 `newline="\n"`）。
3. **C5 改的 PR 模板被我的脚本覆盖了**。他改得对，我的脚本一跑就打回原形，
   他白干一场。**教训：生成器是源头，要改源头而不是改产物。**
4. **9 个人里 5 个人没推分支**。分发包发了、任务指导书写了、但没人推代码，
   M2/M3 的集成链就一直断着。**教训：发包 ≠ 开工。** 我应该用 issue 逐个盯进度，
   而不是等他们自己来。这是我作为组长最该改进的地方。
5. **合并顺序调整晚了**。#43 合入后 main 变红才发现 #40 压着我的修复。
   **每合一个 PR 立刻在 main 上跑 preflight + pytest** 这条规矩写在指导书里，
   我自己没执行到位。
