## 一、数据库详细设计：E-R 图与表结构

### 1.1 实体关系图（E-R）

7 张表、6 组关系（`src/g05/models/` 实际定义）：

```text
                        ┌──────────────┐
                        │  lineage_node │ (血缘节点, node_key 全局唯一)
                        └──────┬───────┘
              upstream_id ┌────┴────┐ downstream_id
                 ┌────────┴─────────┴────────┐
                 │       lineage_edge         │  M:N 关系表（边）
                 │ (upstream_id,downstream_id)│  up/down 均为 FK → lineage_node.id
                 └───────────────────────────┘

┌──────────┐ 1      N ┌──────────────┐ N     1 ┌──────────────┐
│  device   │─────────│ measure_point │─────────│     alarm     │
│ 设备台账  │ RESTRICT │   测点表      │ CASCADE │   告警表      │
│ (软删主表)│─────────│ (版本链核心)   │─────────└──────────────┘
└────┬─────┘ CASCADE  └──────┬───────┘ CASCADE
     │        N              │ N
     └───────► record ◄──────┘
              采集记录表（(point_id,ts)/(device_id,ts) 复合索引）

┌──────────────┐
│  audit_log    │  审计表（旁路记录，append-only：UPDATE/DELETE 被触发器 ABORT）
└──────────────┘  不与业务表建外键，business_key 弱关联 + 行级快照
```

### 1.2 外键与级联策略（编码实现的依据）

| 关系 | ondelete | 设计理由 |
|---|---|---|
| measure_point.device_id | **RESTRICT** | 有测点的设备不允许物理删除（资产保护），业务删除一律走软删 |
| record.device_id | **CASCADE** | 设备物理删除时历史记录随库清理 |
| record.point_id | **CASCADE** | 同上 |
| alarm.device_id / point_id | **CASCADE** | 同上 |
| lineage_edge.upstream_id / downstream_id | 关联 lineage_node | 血缘分发依赖节点存在 |
| measure_point.superseded_by（自引用） | **SET NULL** | 版本链断裂不阻塞删除 |

### 1.3 各表字段与属性

**device（设备台账主表）**——继承 TimestampMixin（created_at/updated_at）+ SoftDeleteMixin（is_deleted/deleted_at/version）

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | Integer | PK, autoincrement | 代理主键 |
| device_code | String(32) | NOT NULL, **UNIQUE**, 索引 | 业务唯一键；软删不释放编号（工业资产编码规范） |
| device_name | String(64) | NOT NULL, 索引 | 设备名称 |
| device_type | String(32) | NOT NULL, 索引 | 设备类型 |
| location | String(128) | NOT NULL | 安装位置 |
| status | String(16) | NOT NULL, default='运行' | 运行/停机/检修/报废；**server_default 兜底裸 SQL 写入** |

复合索引：`ix_device_type_status(device_type,status)`、`ix_device_type_active(device_type,is_deleted)`——列表页高频筛选。

**measure_point（测点表，版本链核心）**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | Integer | PK | 代理主键 |
| device_id | Integer | NOT NULL, FK→device.id (RESTRICT), 索引 | 所属设备 |
| point_code | String(48) | NOT NULL, **UNIQUE**, 索引 | 全局唯一业务键；血缘节点以此为 node_key |
| point_name | String(64) | NOT NULL, 索引 | 测点名称；**改名只改本字段**（point_code 不变→血缘边无需重连，ADR-002） |
| point_type | String(32) | NOT NULL, 索引 | 测点类型 |
| unit | String(16) | NOT NULL | 计量单位 |
| superseded_by | Integer | NULL, 自引用 FK (SET NULL), 索引 | 版本链：指向接替它的新测点 |
| renamed_from | String(64) | NULL | 改名前的历史名称 |
| change_note | Text | NULL | 变更原因（与审计 reason 对应） |

复合索引：`ix_point_device_active(device_id,is_deleted)`、`ix_point_type_active(point_type,is_deleted)`。

**派生属性（@property）**：`device_code`、`device_name`——出参带设备上下文，避免前端只看到裸 device_id。

**lineage_node / lineage_edge**：血缘节点（node_type, node_key 唯一）+ 关系边（upstream_id, downstream_id）；`ix_edge_downstream(downstream_id)` 支撑反向 BFS。

**record / alarm**：采集记录与告警，`(point_id,ts)`、`(device_id,ts)` 复合索引支撑时间区间查询。

**audit_log**：append-only 审计（table_name, record_id, business_key, action, operator, old_value, new_value, reason, trace_id, changed_at）；三组合成索引 `ix_audit_table_time / ix_audit_operator_time / ix_audit_business_time`。

## 二、类与方法设计

### 2.1 模型层类设计（src/g05/models/）

| 类 | 继承 | 核心属性（方法见下） | 设计要点 |
|---|---|---|---|
| Device | Base + TimestampMixin + SoftDeleteMixin | 见 1.3 | passive_deletes=True：物理删除交给数据库外键，ORM 不逐条拉子表（量大时不拖垮进程）；lazy="selectin" 用于 points（列表页避免 N+1） |
| MeasurePoint | 同上 | 见 1.3 | 改名不删行：point_name 更新 + version 自增 + renamed_from 留痕 |
| Record / Alarm | 同上 | 记录与告警字段 | CASCADE 级联 |
| LineageNode / LineageEdge | Base | 节点与边 | 环由 trg_edge_no_self_loop 触发器兜底 |
| AuditLog | Base | 见 1.3 | build() 工厂方法构造；随业务事务一起提交（审计与业务同生共死） |

### 2.2 关键方法设计（src/g05/ 实际实现）

| 方法 | 位置 | 设计说明 |
|---|---|---|
| `impact_of(session, node_type, node_key, direction)` | lineage/impact.py | 影响面 BFS：按层展开边查询，环检测 + 诚实截断三字段（total/returned/truncated_by）；返回 ImpactOut 契约 DTO |
| `register_node(s) / register_edges` | lineage/impact.py | 血缘分发的批量注册入口（bench 与测试同源构造 200 节点图） |
| `import_workbook(session, path)` | importers/bulk_importer.py | 导入主流程：解析→校验→**单事务** device→measure_point 顺序入库→审计；异常整批 rollback（失败零写入） |
| `bulk_insert_mappings` + 分批 flush | importers/bulk_importer.py | 万行性能关键：绕过 ORM 逐行开销，chunk 分批避免内存峰值（实测 1.14s） |
| `build_rejection_note` | importers/bulk_importer.py | 打回单：行号/列/规则/原值，Excel 与 JSON 双格式导出 |
| `validate(df)` | importers/validator.py | 从 config/rules.yaml 编译校验器执行；**只读保证**（入参深比较锁定） |
| `AuditService.record(session, ...)` | audit/service.py | 审计追加唯一入口：随业务事务同生共死；**永不 update/delete** |
| `AuditService.query / export` | audit/service.py | 时间线查询（ix_audit_table_time 命中）+ CSV 导出 |
| `apply_triggers(conn)` | core/schema.py | 装审计不可篡改触发器；**装载后自检**（缺失即 fail-fast，PR #65） |
| `ensure_schema(drop)` / `run_preflight` | core/schema.py · cli.py | 建表 + 触发器 + 自检；preflight 输出 JSON（hard/soft 分级） |
| `cmd_seed / cmd_serve / cmd_seed` | cli.py | seed 执行期间隔离 sys.argv（runpy 透传缺陷修复，PR #68） |

### 2.3 契约层设计（schemas/）

- `dto.py`：10 个冻结 DTO（DeviceIn/Out、PointIn/Out、Page[T]、RenameResult、ImportSummary、AuditOut、ImpactOut、GraphOut）；模型 `__dto_fields__` 与 DTO 字段**逐位比对**（顺序一致）。
- `errors.py`：24 个冻结错误码，1xxx 参数 / 2xxx 业务 / 5xxx 系统；测试强制 1xxx→4xx、5xxx→5xx。

## 三、编码实现说明

| 主题 | 实现要点 |
|---|---|
| 分层 | routes（参数/权限/调 service）→ services/importers（业务）→ models（ORM）→ core（配置/库/审计触发器） |
| 错误处理 | 路由一律抛 `ApiError`（冻结码），全局处理器统一错误体 `{code, message, detail}` + trace_id |
| 配置外置 | config/{app,database,logging,rules}.yaml，`G05_DATABASE__DATABASE__PATH` 等环境变量可覆盖 |
| 日志 | JSON Lines + trace_id 逐行可 json.loads（曾有 6959/14746 行解析失败，#53 修复 + 10 条守护测试） |
| 审计触发器 | `CREATE TRIGGER trg_audit_no_update BEFORE UPDATE ON audit_log BEGIN SELECT RAISE(ABORT,...) END`（DELETE 同理） |
| 软删 | `alive_filter` 统一过滤 is_deleted；软删保留行 + version 链 |
