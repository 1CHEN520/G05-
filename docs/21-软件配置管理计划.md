# G05 软件配置管理计划

> 对应国标 GB/T 8567-2006《软件配置管理计划》。配置管理过程（GB/T 8566 支持过程）成册定义：配置项识别、版本控制、变更控制、配置审计。维护者：A（陈锦妍）。

## 一、配置项识别（什么受控）

| 类别 | 配置项 | 控制方式 |
|---|---|---|
| 源代码 | src/g05/ 全部 .py | Git 分支 + PR 闭环 |
| 测试 | tests/ 全部 + scripts/{fault_inject,bench,reconcile,explain_queries}.py | 同上 |
| 数据模板 | data/sample/sample_devices.xlsx · docs/05 导入模板 | 版本受控 |
| 配置文件 | config/*.yaml（4 个：app/logging/business/validation） | **配置外置**：改配置不改代码 |
| 文档 | docs/ 全部（成册 12+） | PR 评审后合入 |
| 协作规则 | collab/roles.yaml（归属）· AGENTS.md（纪律） | A 维护，变更须登记 |
| 依赖清单 | requirements.txt / environment.yml | 版本锁定（四层结构） |
| 不受控 | data/db/*.db · logs/*.jsonl · __pycache__ | .gitignore 排除（运行产物不入库） |

## 二、版本控制规则

1. **分支策略**：`main` 为主干（受保护语义：仅 PR 合并）+ 功能分支 `feat/{角色}-{主题}` / 文档分支 `docs/{角色}-{主题}`；不直推 main；
2. **提交纪律**：前缀 `feat|fix|docs|chore|test(角色): 描述`；每完成一个功能点提交一次；禁止 `git push -f`；
3. **合并路径**：分支 → push → Pull Request → CI（Ruff/pylint≥9.0/pytest 269）→ 评审 → merge → 删分支 → issue 关闭（必须本人 PR）；
4. **身份纪律**：一工作区一 git 身份（AGENTS.md 3.4）；push 后验证 `git log` 作者与预期一致；
5. **合并后验证**：PR 编号动态获取；merge 后 `gh pr view N --json state` 必须为 MERGED（教训：硬编码编号造成假合并，#86 事故）。

## 三、变更控制流程

```
提出变更（issue）→ 指派归属（roles.yaml）→ 分支开发 → PR+CI → 评审 → 合并 → 关联 issue 关闭
```

- 契约变更（DTO/错误码）升级 A 裁定并留痕 docs/review；
- 实测数据变更同步基线 JSON 与追溯矩阵；
- 教师仓/演示数据的变更须经双人复核（变更单+复核留痕）。

## 四、配置审计

| 审计 | 内容 | 证据 |
|---|---|---|
| 功能配置审计 | 交付功能与需求追溯矩阵一致 | docs/需求追溯矩阵.md（28 条需求→issue→PR 全链） |
| 物理配置审计 | 仓库文件与归属清单一致 | collab/roles.yaml + git shortlog |
| PR 总账 | 合并记录完整可查 | `gh pr list --state merged`（#43~#88 系列） |
| 分支卫生 | 远端仅 main + 归档 tag | `gh api repos/.../branches`（v0-baseline/v0-bootstrap 保留历史） |

## 五、工具与命令（可复现）

```bash
git status / git log --oneline        # 状态与历史
git shortlog -sn                      # 贡献分布
gh pr list --state merged --limit 90  # PR 总账
gh api repos/1CHEN520/G05-/branches   # 分支清单（应仅 main）
pip freeze                            # 依赖锁定核对
```
