- 一个事务内批量写入；分片 `flush` 控内存，但**只有一个 commit**

**验收**：构造一行非法数据 → 整批 0 行入库；成功时 `inserted` 等于有效行数。

## 五、技术要点

### 1. 事务边界只有一处

```python
def import_workbook(session, path, operator):
    reports = [engine.validate(sheet, rows) for sheet, rows in parsed.items()]
    if any(not r.passed for r in reports):
        session.rollback()          # ← 一行都不写
        return ImportResult(ok=False, reports=reports)
    try:
        _write_all(session, parsed)  # 内部只 flush，不 commit
        session.commit()             # ← 唯一的 commit
    except Exception:
        session.rollback()
        raise
```

**反例**：每个 sheet 一个 commit。结果是"设备进了、测点没进"，脏数据留在库里。

### 2. 分批 flush，但不要分批 commit

```python
BATCH = 1000
for i, row in enumerate(rows):
    session.execute(insert(Device), row)   # 或 bulk_insert_mappings
    if i % BATCH == 0:
        session.flush()                    # 只是把 SQL 发出去，事务还开着
```

10000 行一次 `flush` 会把内存和日志顶满；每 1000 行 flush 一次最稳。

### 3. 别用 ORM 逐行 `add()`

```python
# ❌ 慢 5~10 倍：每个对象都要走一次身份映射
for r in rows:
    session.add(Device(**r))

# ✅ 快：绕过 ORM 单对象开销
session.bulk_insert_mappings(Device, rows)
```

万行导入的 30 秒预算，一半耗在解析，一半耗在写入。这里不改，压不到 30s 以内。

### 4. 解析阶段的三个坑

| 坑 | 现象 | 处理 |
|---|---|---|
| 空行 | `{'device_code': None, ...}` 混进数据 | 整行全空则跳过 |
| 表头空格 | `" 设备编号 "` 匹配不上规则 | `strip()` 后比对，`settings.strip_whitespace` 控制 |
| 数字存成文本 | `"123"` 而不是 `123`，`type: int` 校验失败 | 按规则里的 `type` 做一次容错转换 |

### 5. 回执要能定位到 Excel 行号

`report.bad_rows` 存的是 **Excel 里的真实行号**（表头算第 1 行），不是列表下标。
业务方拿着"第 37 行"能直接去改；拿着"第 36 个元素"会一脸懵。

### 6. 上传接口要限制大小

`UploadFile` 不限制大小的话，一个 500MB 的 xlsx 能把内存吃光。上限从 `config/app.yaml` 读，超了返回 413。
