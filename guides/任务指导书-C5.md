## 五、技术要点

### 1. 测试隔离靠 `tmp_path` + `reset_engine`，不靠"记得清理"

```python
@pytest.fixture()
def db_path(tmp_path, monkeypatch):
    path = tmp_path / "test.db"
    monkeypatch.setitem(settings._raw["database"]["database"], "path", str(path))
    reset_engine()          # ← 关键：把已缓存的 Engine 丢掉，否则还连着上一个库
    yield path
    reset_engine()
```

`reset_engine()` 必须在**前后都调**。只在前面调，下一个用例可能复用到上一个的 Engine；只在后面调，第一个用例用的还是全局默认库。

### 2. 测试库也必须装触发器

```python
@pytest.fixture()
def db(db_path):
    engine = get_engine()
    Base.metadata.create_all(engine)
    with engine.begin() as conn:
        apply_triggers(conn)     # ← 少了这句，append-only 测试会假通过
    with session_scope() as session:
        yield session
```

"生产有触发器、测试没有"会导致审计不可篡改的用例在本地永远绿、上线才发现没生效。这也是 `core/schema.py` 把 DDL 集中定义的原因。

### 3. 断言要打到**行为**上，不要打到实现上

```python
# ❌ 脆弱：换个字段名就红，但功能可能没问题
assert report.__dict__["_total_score"] == 87.2

# ✅ 稳：断言语义
assert report.passed is False
assert report.fatal_count == 1
assert any(i.rule == "required" for i in report.issues)
```

**尤其不要断言精确浮点数**。评分是加权计算，`87.20000000000001` 和 `87.2` 都可能出现，用 `pytest.approx` 或断言区间。

### 4. 异常断言要匹配消息，别只 `pytest.raises(Exception)`

```python
# ❌ 任何异常都能过，等于没测
with pytest.raises(Exception):
    ...

# ✅ 精确到异常类型 + 关键信息
with pytest.raises(DatabaseError, match="append-only"):
    db.execute(text("DELETE FROM audit_log"))
```

现有 `tests/test_audit.py` 里还有一处 `pytest.raises(Exception)`，可以顺手收紧成 `DatabaseError`。

### 5. 故障注入的 `kill` 用例：必须真的 `SIGKILL`，不能 `terminate()`

```python
proc = subprocess.Popen([sys.executable, str(tmp_py)], ...)
time.sleep(1.8)      # 让它写一批
proc.kill()          # SIGKILL，模拟断电。terminate() 会走优雅退出，测不出问题
proc.wait(timeout=10)
```

`terminate()` 会让进程正常关闭连接、flush 缓冲，那就不叫"断电"了。测完必须验两件事：

```python
integrity = db.execute(text("PRAGMA integrity_check")).scalar()   # 必须是 "ok"
written = db.execute(select(func.count()).select_from(Device).where(...)).scalar_one()  # 已提交的要能读
```

### 6. 并发用例要断言"计数一致"，不只是"没报错"

```python
expected = threads * per_thread
if errors:
    return False
return actual == expected     # ← 少了这个，丢数据也能"通过"
```

线程数别开太大（8 线程 × 40 条足够）。开 200 线程在机械硬盘上必然超时，那是测试环境问题，不是系统问题。

### 7. CI 的 Python 版本要和本地一致

本地是 **3.12**（pp03），CI 也写 3.12：

```yaml
- uses: actions/setup-python@v5
  with:
    python-version: "3.12"
- run: pip install -r requirements.txt -r requirements-dev.txt -e .
- run: ruff check .
- run: pytest -q --cov=src/g05 --cov-report=term-missing
```

版本不一致会出现"本地绿、CI 红"，而且往往是 `typing` 或 `datetime` 的行为差异，排查成本极高。

### 8. 覆盖率看**核心模块**，不看全局数字

`src/g05/main.py`、`cli.py` 这类胶水代码覆盖率天然低。报告里要分开说：

```bash
pytest --cov=src/g05/models --cov=src/g05/audit --cov=src/g05/importers --cov-report=term-missing
```

`models` / `audit` / `importers` / `lineage` 四个目录 ≥70% 才算达标；整体数字写进 README 时注明口径，别虚报。

### 9. 不许为了让测试绿而放宽断言或跳过用例

这是测试岗最容易犯的错，也是最伤项目的：

| 禁止 | 正确做法 |
|---|---|
| `@pytest.mark.skip("暂时不过")` | 开 issue 给负责人，标 `bug`，用例保留红灯 |
| 把 `assert x == 3` 改成 `assert x >= 1` | 先确认是代码错还是断言错，写进 issue |
| 删掉失败的用例 | 同左 |
| 在 CI 里加 `continue-on-error` | 红灯就是红灯 |

**唯一例外**：环境相关的用例（比如依赖特定磁盘速度的 bench），用 `@pytest.mark.skipif` 明确写清条件。

### 10. bench 必须记环境 + 取中位数

```python
# 单次测量没有意义：第一次有冷启动，后面可能有缓存
times = [measure() for _ in range(3)]
median = sorted(times)[1]
```

报告里必须包含：CPU 型号、内存、磁盘类型（SSD/HDD）、OS 版本、Python 版本、数据量（多少设备/测点）。**没有这些数字的性能报告是不可复现的，等于没写。**
