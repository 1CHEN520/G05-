## 五、技术要点

### 1. 需求必须带数字，否则等于没写

| ❌ 不可验收 | ✅ 可验收 |
|---|---|
| 导入要快 | 10000 行设备+测点导入 < 30s（i5-12400 / SSD） |
| 系统要稳定 | 连续运行 8 小时无内存增长 >10%，强杀后重启可读已提交数据 |
| 查询要快 | 血缘下游查询（深度 5）< 500ms |
| 支持大数据量 | 设备 10 万条 / 测点 50 万条时，列表分页 P95 < 300ms |
| 审计要全 | 任意写操作 100% 产生审计记录，回滚时同步回滚 |

**判据**：这条需求能不能写成一条 `assert`？不能就还没写清楚。

### 2. 追溯矩阵是需求的"体检报告"

```markdown
| 需求 | 模块 | Issue | 负责人 | 验收方式 |
|---|---|---|---|---|
| NFR-P01 万行导入 <30s | importers | G05-27 | C1 周翔 | `bench.py` 输出 |
| NFR-S01 审计不可篡改 | audit | G05-20 | C3 蒋蕊娴 | `verify-immutable` |
```

矩阵里有空缺（某条需求没有对应 issue），说明这条需求没人做——这是文档岗最有价值的产出，比写十页背景介绍有用。

### 3. 文档里每条命令都要**在干净环境**跑一遍

不是"看起来对"，是"我复制粘贴过"。

```bash
# 反例：文档写了这个，但读者机器上没有 g05 命令
g05 preflight

# 正例：给出不依赖 PATH 的写法，并说明两种方式的差别
python -m g05 preflight      # 推荐：不依赖入口脚本
g05 preflight                # 等价，前提是 pip install -e . 成功且 Scripts 在 PATH
```

**验证方法**：新开一个终端（不是你现在这个已经 `activate pp03` 的），照文档从头敲一遍。任何一步报错，就是文档的 bug。

### 4. runbook 的三段式：现象 → 判断 → 处理

```markdown
### 故障 A：服务启动报 database is locked

**现象**：`python -m g05.main` 起来后第一个请求就 500，日志里有 `sqlite3.OperationalError: database is locked`

**怎么判断**：
1. 看 `logs/g05.log` 里是否有 `database is locked`
2. 用 `python -c "import sqlite3; ..."` 试连一次，看是否能拿到写锁
3. 确认是否有另一个进程（另一个终端 / 上次没关的服务）连着同一个 .db

**怎么处理**：
1. `tasklist | findstr python` 找到残留进程，`taskkill /PID xxx /F`
2. 仍不行则删 `data/g05.db-wal`、`data/g05.db-shm`（**先备份 .db**）
3. 重启服务，`curl /healthz` 确认 ok
```

**"怎么判断"这一段最容易漏**。半夜值班的人最需要的是"我怎么知道是这个问题"，不是"这个问题怎么修"。

### 5. 演示脚本要写"预期看到什么"

```markdown
| 时间 | 我说 | 我点 | 预期看到 | 万一没看到 |
|---|---|---|---|---|
| 0:00-1:00 | 项目定位与四问 | — | 首页概览卡片 | 直接切 /docs 讲接口 |
| 3:00-4:30 | 导入 10000 行 | 导入页 → 上传 | 评分条 92 分、0 致命错误 | 用预置的 `data/sample/` 结果截图 |
```

**"万一没看到"这一列是救命列**。现场网络、投影、字体都可能出问题，每一段都要有 Plan B。

### 6. 兜底方案要具体到"打开哪个文件"

```markdown
### 演示环境崩了怎么办
1. **服务起不来**：切到 `docs/demo_script.md` 附录的截图包（`docs/assets/`），逐张讲
2. **数据没了**：`python scripts/init_db.py && python scripts/seed_data.py`（30 秒重建）
3. **完全断网/断投影**：口述 + 白板画四表关系图 + 念追问答案里的数字
```

不要说"那就口头讲"——口头讲什么，要提前写好。

### 7. 踩坑记录的四段式，且必须能对应真实提交

```markdown
## N. 一句话标题

**现象**：（用户/开发者看到什么，带报错原文）
**根因**：（为什么会这样，机制层面）
**解法**：（改了哪一行/哪个文件，带代码）
**预防**：（怎么让这件事不再发生，比如加了测试/加了校验/写进了文档）
```

**"预防"这一段是区分"日记"和"资产"的分界线**。只写"我改好了"的，是日记；写了"以后怎么不再犯"的，才是资产。

现有 `docs/踩坑记录.md` 已有 10 条，你要做的是**核对每一条能不能对应到一次真实提交或故障注入**，对不上的补上 commit hash 或删掉。

### 8. 数字必须有出处

文档里出现任何性能数字，都要能指向一次真实测量：

```markdown
| 指标 | 数值 | 出处 |
|---|---|---|
| 万行导入 | 18.4s | `scripts/bench.py` 2026-10-25 运行，见 docs/06 附录 |
| 血缘查询（深度 5） | 210ms | 同上 |
```

**不许**写"大约""理论上""预计"。没测过就写"未测"，比编一个数字诚实。
