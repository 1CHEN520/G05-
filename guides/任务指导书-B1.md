### G05-06 四表 ER 设计与数据字典（M1，6h）

- 画 ER：`device` / `measure_point` / `record` / `alarm` + `audit_log` + `lineage_node` / `lineage_edge`，共 7 张

**验收**：ER 图能逐字段对到 ORM 类，无遗漏；外键策略有理由。

### G05-08 ORM 声明式模型实现（M2，10h）

- 用 SQLAlchemy **2.0 写法**：`Mapped[...]` + `mapped_column(...)`，不用 1.x 的 `Column`
- 关系用 `relationship(back_populates=...)`，双向都要写
- 每个模型实现 `to_dict()`，审计快照与接口序列化都复用它
- 时间统一 UTC 存，展示层再转本地时区

**验收**：空库上 `Base.metadata.create_all()` 一次成功；双向关系可访问；单测覆盖默认值、时间戳、版本号自增。

### G05-09 索引、约束与外键策略（M2，8h）

- `device_code`、`point_code` 唯一约束
- 测点 → 设备外键；`PRAGMA foreign_keys=ON` **每个连接都要设**（SQLite 默认是关的！）
- 复合索引：`(device_id, is_deleted)`、`(point_type, is_deleted)`
- 用 `EXPLAIN QUERY PLAN` 证明高频查询走索引

**验收**：
```bash

# 期望：FOREIGN KEY constraint failed
```

### G05-10 软删与版本号机制（M2，6h）

- `is_deleted` / `deleted_at` / `version` / `change_note` 四个字段
- 查询默认过滤已删，提供 `include_deleted` 开关
- 改名**不删行**，只 `version += 1` 并写 `renamed_from`

**验收**：软删后默认列表查不到、带开关能查到；连改 3 次 `version` 依次 2/3/4；物理行数不因软删减少。

### G05-11 建库脚本与约束 DDL（M2，5h）

- `scripts/init_db.py` 支持 `--drop`，幂等执行
- 触发器**不要自己写一份**，调 `g05.core.schema.apply_triggers(conn)`
- 建完打印表清单与触发器清单

**验收**：删掉 `.db` 后一条命令重建成功；重复执行不报错；测试夹具与生产共用同一份触发器定义。

## 五、技术要点（AI 最容易写错的地方）

### 1. 必须用 SQLAlchemy 2.0 写法

```python
# ✅ 正确
class Device(Base, TimestampMixin, SoftDeleteMixin):
    __tablename__ = "device"
    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    device_code: Mapped[str] = mapped_column(String(32), nullable=False, unique=True, index=True)
    points: Mapped[list["MeasurePoint"]] = relationship(back_populates="device", lazy="selectin")

# ❌ 错误（1.x 风格，本项目不用）
id = Column(Integer, primary_key=True)
```

**提醒 AI**：不要混用两种风格，也不要用 `declarative_base()`。

### 2. `PRAGMA foreign_keys=ON` 必须每连接设

SQLite 的外键默认**关闭**，只在 `create_engine` 时设一次没用。正确做法是在连接事件里执行：

```python
@event.listens_for(engine, "connect")
def _fk_on(dbapi_conn, _):
    dbapi_conn.execute("PRAGMA foreign_keys=ON")
```

如果 `_check_database()` 的 `foreign_keys` 是 `false`，说明这里漏了。

### 3. 外键 `ondelete` 要分场景

| 关系 | 策略 | 理由 |
|---|---|---|
| 测点 → 设备 | `CASCADE` | 设备物理删除时测点无宿主，留着就是孤儿 |
| 记录 → 测点 | `CASCADE` | 同上 |
| 告警 → 设备 | `RESTRICT` 或 `CASCADE` | 告警是历史证据，倾向不随设备消失，选 `RESTRICT` 并写进 ADR |

**关键**：业务层用软删，`cascade` 只在物理删除时生效。别把软删和级联混在一起谈。

### 4. `lazy` 策略按访问模式选

- 列表页要带出设备编号 → `lazy="selectin"`（避免 N+1）
- 单条详情才用到 → `lazy="select"`
- 绝不无脑用 `lazy="joined"`，大表会拖垮查询

### 5. 时间统一 UTC

```python
created_at: Mapped[datetime] = mapped_column(
    DateTime(timezone=True), nullable=False, default=lambda: datetime.now(timezone.utc)
)
```

不要 `datetime.now()`（本地时间），否则跨时区/夏令时会出鬼。

### 6. 索引不是越多越好

`is_deleted` 单独建索引几乎没用（基数只有 2），要建**复合索引**：`(device_id, is_deleted)`。建完必须用 `EXPLAIN QUERY PLAN` 验证真的走了索引，否则删掉。

## 七、边界

| 不许做 | 说明 |
|---|---|
| 改 `src/g05/core/schema.py` 的触发器 | 那是 A 的文件，你只调用 `apply_triggers()` |

| 在模型里写业务逻辑 | 模型只描述结构，逻辑放 `services/` |
