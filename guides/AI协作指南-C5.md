# AI 协作指南 · C5（韩永健）

> 读者：你自己。**《任务指导书-C5》是给 AI 读的，这份是给你读的。**  
> 你是唯一"不写功能但能让别人返工"的角色。  
> 所以你的 AI 用法核心是：**先让它写"能失败的测试"，再让它修。**

---

## 一、用哪种 AI

| 优先级      | 工具形态                           | 具体建议                          | 为什么适合你                         |
| -------- | ------------------------------ | ----------------------------- | ------------------------------ |
| **主力**   | 能跑命令的 Agent 型（Claude Code 最合适） | 优先选能长时间连续执行命令的                | 你的工作是"跑 → 看红 → 定位 → 再跑"，循环次数最多 |
| **主力补充** | 推理型模型                          | 分析"这条测试为什么 flaky"             | 间歇性失败的原因往往很绕（时序、事务隔离、缓存）       |
| **备选**   | 网页对话                           | 查 pytest 插件、GitHub Actions 语法 | 够用，但它不能替你跑 `pytest`            |
| **不推荐**  | 纯 Tab 补全                       | —                             | 补出来的测试往往是"测实现"而不是"测行为"，一改代码就红  |

**一条硬要求**：每次让它写测试，先问"**这条测试在什么情况下会失败？**" 答不出"什么情况下红"，这条测试就没有价值。

| ------------------------ | ------------------ |

## 四、项目初始化提示词（第一次对话，整段复制）

```
你是我的结对开发 AI。我是 G05 项目的 C5（测试与性能压测），真名韩永健。

## 我的角色边界（最重要）
- 我不改 src/g05/** 的业务代码。发现 bug → 写 issue 给对应负责人
- 我负责：tests/conftest.py、tests/test_api.py、scripts/fault_inject.py、scripts/bench.py、.github/workflows/**
- pyproject.toml 和 .github/pull_request_template.md 归 A，我要改走 issue + PR
- 禁止 skip / xfail / 放宽断言来让 CI 变绿

## 硬性技术约束
- pytest 8.x，每个测试用独立临时 SQLite（tmp_path + reset_engine），互不污染
- 测试库必须装和生产同一份触发器（apply_triggers）
- CI 的 Python 版本必须和本地一致：3.12
- 代码风格：类型注解齐全、中文注释、行宽 110

## 第一步：读文件，只输出清单，不要写代码
1. guides/任务指导书-C5.md            ← 我的岗位说明书，最重要
2. tests/conftest.py                  ← 夹具地基
3. tests/test_models.py / test_audit.py / test_lineage.py / test_importer.py
4. scripts/fault_inject.py            ← 五类故障注入
5. pyproject.toml                     ← pytest / ruff / coverage 配置
6. src/g05/cli.py                     ← preflight 的 hard/soft 区分

## 第二步：回答六个问题（找不到就说"文件里没有"，不许猜）
1. 夹具链 db_path → db → sample_devices 的依赖关系是什么？reset_engine 为什么前后都要调？
2. 现在共有多少条用例？按模块分布是怎样的？哪一块最薄？
3. 现有用例里，哪些断言的是"实现"而不是"行为"？（改个字段名就红的那种）
4. 故障注入的 kill 用例为什么必须 proc.kill() 而不是 terminate()？
5. 并发用例除了"没报错"，还必须断言什么？
6. 覆盖率应该看全局还是看核心模块？为什么？

## 第三步：给我一张"缺口表"
按六个模块（模型/校验/血缘/审计/导入/接口）列出：
现有用例数 / 明显缺失的场景 / 优先级（P0 阻断/P1 重要/P2 可选）。
表格形式，不要写代码。

## 工作约定
1. 写测试前先说：测什么行为、什么情况下会红、断言什么
2. 不许为了让测试通过而改业务代码或放宽断言
3. 不许编造测试结果，没跑过就说"未验证"
4. 每条新用例都要能回答"它能挡住哪种回归"
5. 中文回答
```

### 它应该怎么回答（判断有没有读懂）

| 检查点  | 合格回答                                               |
| ---- | -------------------------------------------------- |
| 夹具链  | 说得出 `db_path` 改配置 + `reset_engine` 丢缓存；**前后都调**的原因 |
| 用例分布 | 能报出真实数字（不是"大约 40 条"）                               |
| 脆弱断言 | 点得出 `assert report.__dict__["_total_score"]` 这类    |
| kill | 说得出 `terminate()` 走优雅退出、会 flush，测不出断电              |
| 并发   | 说得出必须断言"入库条数 == 预期"，否则丢数据也能"通过"                    |
| 覆盖率  | 说得出核心四模块 ≥70%，胶水代码不算                               |

## 五、日常四类提示词

### 5.1 写测试

```
请为 <模块/接口> 写测试，按顺序输出：
1. 要测的行为清单（每条一句话）
2. 每条对应的"什么情况下会红"（如果答不出，删掉这条）
3. 边界表：空数据 / 单条 / 多条 / 超限 / 非法输入
4. 代码（用现有夹具，不新建重复夹具）
5. 跑一遍，把真实输出贴给我

先给 1、2，我确认后再写。
```

**第 2 步是过滤器**。答不出"什么时候红"的测试，写出来只是增加维护成本。

### 5.2 排错（测试红/绿得可疑）

```
现象：<比如"这条用例单独跑绿，全量跑红">
请按顺序判断：
1. 是不是测试之间共享了状态（同一个 db / 同一个临时文件）？
2. 是不是依赖执行顺序？
3. 是不是时间相关（UTC/本地时区、utcnow 精度）？
4. 是不是随机性（没有固定 seed）？

每种给一条验证方法。先别改代码。
```

**"单独绿、全量红"= 状态污染**，十有八九是 `reset_engine` 漏了或夹具作用域写成了 `session`。

### 5.3 CI 排错

```
GitHub Actions 报错如下：<贴日志关键段>
本地同样的命令是绿的。

请：
1. 先判断是"环境差异"（Python 版本/依赖/OS）、"路径差异"（大小写、分隔符）还是"时序差异"
2. 给一条能在本地模拟 CI 环境的命令
3. 验证后再改 workflow
```

Windows 本地 + Linux CI 最常见的坑：**文件名大小写**。`import G05` 在 Windows 能过，在 Linux 必炸。

### 5.4 提交前自检

```
我要提交了，做提交前检查（只读不改）：
1. git diff --stat：只改了我名下的 5 个文件吗？
2. 有没有新增 skip / xfail？（红线）
3. 有没有放宽已有断言？
4. 新增用例数是多少？总数现在多少？
5. 给我一条 type(scope): 格式的 commit message
```

## 六、你这个角色专属的技巧

### 1. 让 AI 写"故意失败"的测试，验证门禁真的有用

```
请写一条测试，故意让某个模块出错，验证 CI 会变红：
1. 造一个必然失败的断言（比如断言一个不存在的字段）
2. 说明怎么在 CI 上看到它红
3. 说明怎么撤回
这条测试不进 main，只用来生成"CI 变红"的截图证据。
```

G05-05 的验收要求"故意提交失败用例 CI 变红（附截图）"，这是拿证据的标准做法。

### 2. 故障注入的每一类，都要问"如果它没被拦住，用户会看到什么"

```
对五类故障（孤儿/篡改/脏数据/强杀/并发），请分别回答：
如果系统没防住，用户会在界面上看到什么现象？会在哪个页面暴露？
```

答案会让你的输出更有说服力——答辩时讲"如果没拦住，台账里会出现查不到设备的测点"，比讲"外键约束生效"生动得多。

### 3. bench 用"同一台机器、三次中位数、记录环境"

```
写 scripts/bench.py，要求：
1. 四类指标：万行导入 / 血缘查询（深度 3、200 节点）/ 列表分页 / 审计查询
2. 每类跑 3 次，取中位数（不要取平均，第一次有冷启动）
3. 自动采集环境信息：CPU 型号、内存、磁盘、OS、Python 版本、数据量
4. 输出 Markdown 表格，可直接贴进报告
5. 每类指标附一行"复现命令"
```

**"取中位数不取平均"**&#x662F;因为第一次测量含冷启动，会拉高平均值，报告不好看也不真实。

### 4. 覆盖率报告要能定位到"哪几行没测"

```bat
python -m pytest --cov=src/g05 --cov-report=term-missing --cov-report=html -q
```

`term-missing` 会打出具体行号。让 AI 按缺失行号分类：

```
这是 coverage 的 term-missing 输出：<粘贴>
请把未覆盖的行按"可测 / 难测 / 不值得测"三类归档，
并给出"可测"那部分应该补什么用例（按优先级排序）。
```

### 5. 并发用例别开太大

```
我的并发用例开 8 线程 × 40 条。请评估：
1. 这个规模能测出 database is locked 吗？
2. 开到多少会开始测出"环境问题"而不是"系统问题"？
3. 机械硬盘和 SSD 上的合理值分别是多少？
```

**测试要测系统，不要测硬盘。** 开 200 线程在机械盘上必然超时，那是环境问题。

## 七、红线（对 AI 说什么都不行）

| 不许                                      | 为什么                |
| --------------------------------------- | ------------------ |
| 加 `@pytest.mark.skip` / `xfail` 让 CI 变绿 | 红灯就是红灯，掩盖问题        |
| 把 `assert x == 3` 改成 `assert x >= 1`    | 放宽断言 = 放弃检测        |
| 删掉失败的用例                                 | 同上                 |
| 在 CI 里加 `continue-on-error`             | 红灯挡不住合并，等于没 CI     |
| 改 `src/g05/**` 的业务代码                    | 越权，且没人 review      |
| 改 `pyproject.toml` 的 `dependencies`     | 依赖归 A              |
| 让测试连生产库/共享库                             | 会互相踩，必须 `tmp_path` |
| 为了让 bench 好看而缩小数据量                      | 报告失真，且答辩时被问数据量就穿帮  |
| 相信"应该能过"                                | 必须贴真实输出            |

## 八、常见翻车与应对

| 现象             | 原因                | 应对                                         |
| -------------- | ----------------- | ------------------------------------------ |
| 单独绿、全量红        | 状态污染              | 检查 `reset_engine` 前后都调、夹具作用域               |
| Windows 绿、CI 红 | 文件名大小写 / 路径分隔符    | 统一用 `pathlib`，import 严格小写                  |
| 触发器测试假通过       | 测试库没装触发器          | conftest 里调 `apply_triggers`               |
| 断言浮点数偶尔红       | 精确比较              | 用 `pytest.approx` 或区间                      |
| kill 用例测不出问题   | 用了 `terminate()`  | 改 `proc.kill()`（SIGKILL）                   |
| 并发用例报 locked   | 没配 `busy_timeout` | 查 `core/db.py` 的 PRAGMA                    |
| CI 装依赖慢到超时     | 没缓存 pip           | 加 `actions/cache` 或 `setup-python` 的 cache |
| 覆盖率虚高          | 只统计了被 import 的文件  | 用 `--cov=src/g05` 显式指定                     |
| 别人的 PR 让你的用例红了 | 契约变更              | 先确认是不是 A 批准的变更，再改断言                        |
