## 五、技术要点（这一节决定你的审计是"真"还是"看起来有"）

### 1. 旧值必须在**加载时**拍快照

这是最容易做错、也最难测出来的一个点。

```python
# ❌ 错误：flush 时对象已经被改过了，这里取到的"旧值"其实是新值
for obj in session.dirty:
    old = _snapshot(obj)          # 拿到的是修改后的值！

# ✅ 正确：对象刚从库里加载出来就拍一份，挂在实例上
@event.listens_for(session_factory, "loaded_as_persistent")
def _capture_old(session, instance):
    if instance.__tablename__ in _AUDITED_TABLES:
        instance._g05_old_snapshot = _snapshot(instance)
```

**为什么事件名是 `loaded_as_persistent`**：它在对象被 ORM 从数据库取出、变为持久态的那一刻触发，此时属性还是库里的原值。`before_flush` 触发时属性已经被业务代码改完了。

**自测方法**：改一个字段，看审计记录的 `old_value` 里是不是**改之前**的值。如果不是，这条审计就是废的。

### 2. `before_flush` 里只能 `session.add()`，绝不能 `commit()` / `flush()`

```python
# ❌ 会导致无限递归或事务状态错乱
@event.listens_for(session_factory, "before_flush")
def _before_flush(session, flush_context, instances):
    session.commit()      # 灾难

# ✅ 只 add，让它跟着本次 flush 一起落库
session.add(AuditLog.build(...))
```

同一个 flush 里 add 的对象会在**这次** flush 中被写入，所以审计与被审计变更天然同事务——这是"回滚时审计一起回滚"的实现基础，不需要额外写代码。

### 3. 显式审计 vs 自动审计：用标记去重，不要靠"猜"

业务层（C4 的 `rename_point`）需要写带 `reason` 的语义化审计（`RENAME`），但自动埋点也会给它记一条 `UPDATE`。两条记录重复且后者没有原因。

解法是一个实例级标记：

```python
# 业务层：我这条我自己记，你别插手
point._g05_skip_audit = True

# 自动埋点：看到标记就跳过，并把标记清掉（避免影响下一次 flush）
if getattr(obj, "_g05_skip_audit", False):
    obj._g05_skip_audit = False
    continue
```

**三个循环（new / dirty / deleted）都要检查这个标记**，漏一个就会产生重复审计。

### 4. append-only 必须有两道防线，少一道都不算数

| 防线 | 位置 | 拦得住谁 |
|---|---|---|
| 应用层不提供 update/delete 方法 | `AuditService` | 走正常代码路径的人 |
| 数据库触发器 `RAISE(ABORT)` | `core/schema.py` | 直连数据库、写 SQL 的人、DBA |

只有第一道，一句 `UPDATE audit_log` 就破了；只有第二道，应用层还是会有人写错。**答辩时老师大概率会现场敲一句 SQL 试你**，触发器是唯一能救场的。

```sql
CREATE TRIGGER IF NOT EXISTS trg_audit_no_update
BEFORE UPDATE ON audit_log
BEGIN
    SELECT RAISE(ABORT, 'audit_log is append-only: UPDATE forbidden');
END;
```

### 5. 触发器只在表存在时装

`apply_triggers()` 会先查 `sqlite_master`，用正则从 DDL 里抠出 `ON <table>` 再判断。原因：骨架阶段 `lineage_edge` 表可能还没合进来，硬装会让整个应用起不来。

```python
tables = {row[0] for row in conn.execute(text("SELECT name FROM sqlite_master WHERE type='table'"))}
for ddl in TRIGGERS:
    m = re.search(r"\bON\s+([A-Za-z_][A-Za-z0-9_]*)", ddl)
    if m and m.group(1) not in tables:
        continue        # 表还没有，跳过；等模块合入后重启自动补上
    conn.execute(text(ddl))
```

你改这段代码时，**不要退回"无条件执行"**——那是组长为了让大家能并行开发特意做的容错。

### 6. `verify-immutable` 接口必须自己 `rollback`

```python
try:
    db.execute(text("UPDATE audit_log SET operator='hacker' WHERE id=(SELECT MIN(id) FROM audit_log)"))
    db.commit()
    checks.append({"operation": "UPDATE", "blocked": False, "detail": "未拦截（不合规！）"})
except Exception as exc:
    db.rollback()          # ← 少了这句，会话进入 aborted 状态，后续查询全报错
    checks.append({"operation": "UPDATE", "blocked": True, "detail": str(exc)[:160]})
```

而且 `detail` 要截断（160 字符够），SQLite 的错误串可能很长，前端展示会撑破布局。

### 7. 查询轴用 `business_key`，不用 `record_id`

`record_id` 是自增主键，软删后重建同编号设备会得到新 id，历史就断了。`business_key`（`device_code` / `point_code`）是业务上稳定的标识，跨版本追同一实体才对。

```python
def history_of(session, business_key: str, table_name: str | None = None) -> list[AuditLog]:
    """时间线用正序（asc），列表页用倒序（desc）—— 两个场景别用同一个排序。"""
```

### 8. 时间统一 UTC，`DateTime(timezone=True)`

`changed_at` 用 `utcnow()` 默认值，前端展示时再转本地时区。混用本地时间会让"按时间范围查询"在跨时区/夏令时上出错，也会让时间线顺序错乱。

## 七、边界

| 不许做 | 说明 |
|---|---|
| 给 `AuditService` 加 `update` / `delete` 方法 | 红线。哪怕只是"内部调试用"也不行 |
| 在 `before_flush` 里 `commit` / `flush` | 事务会炸 |
| 用 `record_id` 代替 `business_key` 做历史查询 | 软删重建后历史断裂 |
| 把 `old_value` 在 flush 时现取 | 取到的是新值，审计失真 |
| 改 `_AUDITED_TABLES` 之外的业务表逻辑 | 那是 B1/C4 的地盘 |
| 未经 issue 直接改 `core/schema.py` | 跨边界文件，必须走 PR + A 评审 |
| 去掉 `apply_triggers` 的表存在性判断 | 会让骨架阶段起不来 |
| 让审计表和业务表用不同事务 | 会出现"业务失败但审计留下"的假记录 |
