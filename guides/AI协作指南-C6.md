# AI 协作指南 · C6（王新宇）

> 读者：你自己。**《任务指导书-C6》是给 AI 读的，这份是给你读的。**  
> 你写的东西是**老师唯一会逐字读的部分**，也是你组员唯一会反复查的部分。  
> 所以你的 AI 用法核心是：**让它写完，然后你自己照着做一遍。**

## 一、用哪种 AI

| 优先级      | 工具形态                                  | 具体建议            | 为什么适合你                              |
| -------- | ------------------------------------- | --------------- | ----------------------------------- |
| **主力**   | 网页对话（DeepSeek / Kimi / 通义千问 / Claude） | 任选，中文表达好的优先     | 你的产出是**文字**，不需要它跑代码；长文改写、结构重排，网页版够用 |
| **主力补充** | 能读本地文件的 Agent 型                       | 用来"核对文档和代码是否一致" | 文档里的字段名、命令、路径必须和仓库对得上，只有能读文件才能核对    |
| **备选**   | 语音转文字                                 | 彩排时录下来转文稿       | 演示脚本的措辞靠"说顺了"改，不靠"想顺了"              |
| **不推荐**  | 只做"润色"的工具                             | —               | 你的问题不是文笔，是**准确性和可执行性**              |

**一条硬要求**：任何涉及命令、字段、路径的内容，**必须让 AI 去仓库里核对，不许凭印象写**。它编一个 `python -m g05.start` 出来，你照抄进文档，全组人都会踩。

## 三、环境配置（约 20 分钟）

### 3.1 手动四步

打开 **Anaconda Prompt**：

```bat
conda --version
cd /d D:\
git clone <组长给你的仓库地址> g05
cd g05

conda env create -f environment.yml
conda activate pp03
:: 报 conda-launchers 找不到时：conda create -n pp03 python=3.12 pip -y

powershell -ExecutionPolicy Bypass -File .\setup_pp03.ps1

xcopy /E /Y <分发包路径>\files\* .
```

### 3.2 把这段提示词发给 AI

```
我要在 Windows 上配 G05 项目环境，请当陪跑员，一次只给一步。

背景：Python 3.12 + SQLAlchemy 2.0 + FastAPI + SQLite，四层环境。
第 1 层 conda 只装 python 和 pip，其余全 pip。根目录 D:\g05，已有 setup_pp03.ps1。
已知坑：conda-launchers 元数据损坏、editable 指向别的目录、conda activate 静默失败。

每步：命令 + 预期输出 + 失败判断。
最后四条验收：pip check / import g05 路径 / pytest -q / 启动服务后 curl /healthz。

额外要求：每给一条命令，都用"普通人第一次操作"的视角检查一遍——
有没有前提没写（比如要先 cd）、有没有环境依赖没写（比如必须在 Anaconda Prompt 里）。
```

**最后那段"额外要求"就是你的职业习惯**：你是文档岗，AI 写命令时默认"读者已经知道上下文"，你要逼它补上。

### 3.3 四条验收

```bat
python -m pip check
python -c "import g05; print(g05.__file__)"
python -m pytest -q
python -m g05 serve
:: 另一个窗口
curl -s http://127.0.0.1:8000/healthz
```

你自己装成功不算数——**G05-07 的验收是"至少 2 名组员照文档独立装成功并回帖"**。所以这一步你要顺手把 `docs/04` 的问题记下来。

```
你是我的技术写作 AI。我是 G05 项目的 C6（文档与运维），真名王新宇。

## 我的角色边界
- 我写文档，不改代码。发现代码有 bug → 写 issue 给负责人

2. 每条命令必须在干净终端验证过，不许写"应该可以"
3. 每个性能数字必须有出处（哪次测量、什么环境）
4. 故障预案必须三段式：什么现象 → 怎么判断 → 怎么处理

1. 现有非功能需求里，哪几条是"不可验收"的（没有数字）？逐条列出来
```

## 五、日常四类提示词

### 5.1 写文档章节

```
请写 <文档> 的 <章节>，要求：
1. 读者画像：<谁在读，他关心什么，他有什么前置知识>
2. 每条结论后面能跟一条"依据"（文件路径 / 命令 / 实测数据）
3. 能用表格的不要用段落
4. 命令要写成可复制的代码块，标注在哪个终端执行
5. 写完自己检查一遍：有没有"大约/理论上/应该"

先给我章节大纲（三级标题），我确认后再写正文。
```

**先大纲再正文**，能省掉大量返工——AI 写长文容易跑题，大纲能把方向锁住。

### 5.2 把"不可验收"改成"可验收"

```
下面这些需求是不可验收的，请逐条改写：
<粘贴需求列表>

每条改写后必须包含：指标名 + 阈值 + 测量条件（数据量/环境）+ 测量方法。
如果某条无法量化，说明为什么，并给出替代的验收方式（比如"人工演练通过"）。
用表格输出：原表述 / 改写后 / 测量方法。
```

### 5.3 写故障预案

```
请为 <故障场景> 写预案，严格三段式：

**现象**：值班的人第一时间看到什么（界面/日志/命令输出，带原文）
**怎么判断**：3 步以内，每步一条命令或一个观察点，能确认"就是这个问题"
**怎么处理**：编号步骤，每步一条命令，含"处理完怎么确认好了"

约束：
- 不许出现"检查一下配置"这种没有具体命令的话
- 涉及删文件/改数据的步骤，必须先写"备份"
- 每步都要能在一个终端里复制执行
```

### 5.4 提交前自检

```
我要提交了，做提交前检查（只读不改）：
1. git diff --stat：只改了我名下的 7 个文档吗？
2. 文档里出现的每个命令，能不能在仓库里找到对应的脚本/入口？
3. 有没有出现"大约/理论上/预计/应该可以"？（搜出来列给我）
4. 有没有性能数字没写出处？
5. 给我一条 type(scope): 格式的 commit message
```

## 六、你这个角色专属的技巧

### 1. 让 AI 用"新人视角"审自己的文档

```
假设你是一个刚拿到这个仓库、从没听过 G05 的人，只有这份文档。
请逐段指出：
1. 哪一步我会卡住（缺前提/缺路径/缺权限说明）
2. 哪句话我看不懂（术语没解释）
3. 哪个命令我不敢执行（不知道会发生什么）
按"会卡住的程度"排序。
```

这个提示词比"帮我优化文档"有用十倍。**"我不敢执行的命令"**&#x5C24;其重要——`rm`、`drop`、`--force` 这类必须先说清后果。

### 2. 让 AI 从代码里"反推"文档，而不是自己编

```
请从以下文件里提取事实，不要推测：
- src/g05/cli.py：有哪几个子命令？各自的参数和输出是什么？
- config/*.yaml：有哪些可配置项？默认值是什么？
- scripts/*.py：每个脚本怎么调用、参数是什么？

输出表格：命令 / 作用 / 参数 / 输出示例。
找不到的写"代码里没有"。
```

**文档与代码不一致是最丢分的**。让 AI 从代码反推，比让它"根据理解写"可靠得多。

### 3. 演示脚本要按"秒"切，不按"段"切

```
请把演示脚本改成时间轴表格，每行 30-60 秒：
| 起止时间 | 我说什么 | 我点什么 | 预期看到什么 | 万一没看到 |

要求：
1. 总时长 ≤10 分钟（含开场和收尾）
2. 每段必须有"万一没看到"的兜底
3. "我说什么"要写成可以直接念的口语，不是提纲
4. 至少 3 处埋"钩子"（这里有个坑我们踩过 / 这个数字是这样测出来的）
```

**按秒切**是因为彩排时你会发现"讲 2 分钟"实际讲了 4 分钟。表格能让你砍得下去。

### 4. 追问答案要"指得出去"

```
准备 6 个高频追问的标准答案，每个答案必须包含：
1. 一句话结论
2. 一个数字（有出处）
3. 一个"你可以现在就验证"的入口（命令 / 文件路径 / 页面位置）

追问方向参考：为什么用 SQLite / 审计怎么保证不可篡改 / 血缘会不会死循环 /
导入为什么能整批回滚 / 性能数据怎么来的 / 为什么不用现成的元数据平台。
```

第 3 条是分水岭：能当场打开给人看，和只能说"我们实现了"，是两个档次。

### 5. 踩坑记录要"能对上账"

```
请核对 docs/踩坑记录.md 的每一条，逐条回答：
1. 现象描述里有没有具体报错原文？
2. 根因是不是机制层面的解释（不是"配置错了"这种同义反复）？
3. 解法有没有具体到文件/代码？
4. 预防措施是不是可执行的（加了测试/加了校验/写进了文档）？
5. 能不能对应到一次真实提交（commit hash）或一次故障注入？

答"否"的条目，标出来让我补。
```

## 七、红线（对 AI 说什么都不行）

| 不许                              | 为什么                         |
| ------------------------------- | --------------------------- |
| 编造性能数字                          | 学术诚信，且答辩被要求复现就穿帮            |
| 写没跑过的命令                         | 同上                          |
| 改 `src/g05/**` 的代码              | 发现 bug 开 issue，你改了没人 review |
| 改 `README.md` / `docs/00/02/03` | 归 A                         |
| 用"大约/理论上/预计"                    | 模糊表述 = 不可验收                 |
| 把 runbook 写成"理论应该这样"            | 必须是自己实操过的                   |
| 演示脚本超过 10 分钟                    | 超时会被打断，最后最有说服力的验证讲不完        |
| 让 AI "润色"时改动了技术事实               | 润色只改表达，不改数字、命令、字段名          |

## 八、常见翻车与应对

| 现象             | 原因                     | 应对                   |
| -------------- | ---------------------- | -------------------- |
| 组员照文档装不上       | 命令缺前提（没写 `cd`、没写用哪个终端） | 让新人视角的 AI 审一遍 + 真找人试 |
| 文档里的字段名和代码不一致  | 凭印象写的                  | 让 AI 从代码反推           |
| 演示超时           | 每段都超 30 秒              | 按秒切表，砍掉一半铺垫          |
| 答辩被追问卡住        | 答案里没有可验证的入口            | 每个答案配一条命令/路径         |
| 踩坑记录像日记        | 只有"我改好了"没有"怎么防"        | 补"预防"段               |
| 巡检清单没人用        | 项太多、阈值不明确              | 压到 8 项以内，每项给阈值和处置    |
| 需求被老师问"这条怎么验收" | 没数字                    | 全部改写成"指标+阈值+测量条件"    |
| runbook 演练失败   | 写的步骤自己没走过              | 真找一个人演练一次，按他的卡点改     |
