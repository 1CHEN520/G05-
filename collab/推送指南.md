# G05 协作推送指南（不整包推远端）

> 一句话：**组长只推骨架，每人只推自己那份文件。**
> 这样每个 PR 的 diff 天然只包含一个人负责的代码，评审、追溯、贡献度统计全都干净。

---

## 零、为什么不能一次性把项目推上去

一次性 `git push` 全量代码，会带来三个后果：

1. **没人认领**：仓库里 85 个文件一次到位，谁写了什么说不清，贡献度表只能编
2. **PR 变成摆设**：没有"从无到有"的提交过程，评审、讨论、返工这些过程性证据全都没有
3. **出问题无法定位**：线上出 bug，`git blame` 全指向同一个人（组长）

所以本项目采用 **骨架 + 分角色分支** 的方式：

```
main ──● 骨架（A）────────● M2 内核合并────────● M3 功能合并────────● M4 验收
         \                   /                    /                   /
          feat/b1-orm-core ─●                    /                   /
          feat/b2-lineage ─────────────────────●                    /
          feat/c1-importer ───────────────────●                     /
          ...                                                        /
          feat/c6-docs-ops ────────────────────────────────────────●
```

## 一、组长（A）只做这 5 件事

> **状态：第 1~4 步已完成**（2026-10-28）。远端 `main` = `3ced4c1`，71 个文件。
> 仓库地址：`https://github.com/1CHEN520/G05-`（注意仓库名末尾有个 `-`）

```bash
# 1. 在 GitHub 建空仓库（不要勾 README / .gitignore / license，要纯空）
#    实际仓库名：G05-

# 2. 关联远端
cd D:\G05
git remote add origin https://github.com/1CHEN520/G05-.git

# 3. 只把骨架做成一个干净的初始提交（不碰工作区，也不推 master）
#    骨架 = dist/roles/A/files/ 里的 71 个文件
#    用临时索引构造一个孤儿提交，master 上的完整历史原样保留
export GIT_INDEX_FILE=/d/G05/.git/skel.index
git read-tree --empty
find dist/roles/A/files -type f | sed 's|^dist/roles/A/files/||' > .git/skel-files.txt
git add --pathspec-from-file=.git/skel-files.txt
TREE=$(git write-tree)
COMMIT=$(git commit-tree "$TREE" -F .git/skeleton-msg.txt)
git branch main "$COMMIT"
unset GIT_INDEX_FILE

# 4. 推送（只有这一次是组长直推 main）
git push -u origin main

# 5. 打开分支保护：Settings → Branches → Add rule
#    - 分支名 main
#    - Require a pull request before merging（必开）
#    - Require approvals: 1
#    - Require status checks: CI（C5 建好流水线后勾上）
```

> **为什么不用 `git branch -M main` 再推**：那样会把 master 上的全量历史（含所有人代码）一起推上去，
> 等于一次性全量发布，正是这套流程要避免的。
> 现在 `master` 是组长本地的全量备份，**永远不推**；远端 `main` 只有骨架。
> 组长后续要往 main 加东西（比如改这份文档），也必须走 PR，不能直推。

> `dist/roles/A/files/` 由 `python scripts/make_role_bundles.py` 生成。
> 组长不要把自己那份"全部代码"推上去——**组长的职责是骨架与集成，不是替所有人写完**。

**骨架推上去之后是什么状态**（已实测）：

```bash
python -m g05 preflight
# passed: true
# soft_failures: ["静态资源", "校验规则", "数据库与触发器"]
#   ↑ 分别对应 C4 的 web/、C2 的 rules.yaml、B1 的 models/
python -m g05 serve
# 服务能起，首页返回占位页；日志里会打 route.module.missing 警告，
# 提示哪些模块还没合进来。等对应 PR 合并后警告自动消失。
```

也就是说：**骨架是"能跑但功能为空"的**，preflight 的 `soft` 项就是"还没合进来的模块"清单，不是环境装错了。

## 二、每个组员做这 6 步

先确认自己拿到两样东西：**仓库地址** + **自己的角色代号**（A / B1 / … / C6）。

```bash
# 1. 克隆（第一次）
git clone https://github.com/1CHEN520/G05-.git
cd G05-

# 2. 建自己的分支（只建一次，名字照 roles.yaml 里的 branch）
git checkout -b feat/c1-importer

# 3. 把自己的文件包覆盖进来（files/ 里就是按原相对路径排好的文件）
#    包结构：dist/roles/C1/{_bundle/说明, files/要拷进仓库的内容}
cp -r /path/to/dist/roles/C1/files/* .

# 4. 只提交自己包里的文件（先自查）
git status --short
git add -A
git commit -F /path/to/dist/roles/C1/_bundle/COMMIT_MSG.txt

# 5. 推分支
git push -u origin feat/c1-importer

# 6. 到 GitHub 上开 Pull Request
#    base: main  ←  compare: feat/c1-importer
#    标题照 issue： [C1] 批量入库与整批原子回滚
#    正文勾选 PR 模板里的检查项，填关联 issue 编号
```

## 三、三条硬规矩

### 1. 只改自己包里的文件

提交前自查：

```bash
git diff --name-only origin/main...HEAD
```

出现的路径必须全部在自己 `dist/roles/<代号>/` 的清单里。出现别人的文件，说明你跑错分支或者顺手改了不该改的东西。

### 2. 要动公共文件，先发 issue

公共文件指这三类，**归 A 所有**：

| 文件 | 为什么不能随便动 |
|---|---|
| `src/g05/schemas/dto.py` | 接口契约，一改所有模块都要跟 |
| `config/*.yaml` | 配置键，一改所有人本地的值都变 |
| `src/g05/models/base.py` | 所有表共用基类 |

流程：**开 issue 说明要改什么 → A 改 → 你 `git rebase origin/main` 再继续**。
不要"我顺手改一下，反正只是加个字段"——这是多人项目最常见的翻车方式。

### 3. 合并按依赖顺序，不要抢

```
M1 骨架（A）
  ↓
M2 B1 模型 → C3 审计模型 → B2 血缘表
  ↓
M3 C4 接口 → C1 导入 → C2 校验 → B2 影响面
  ↓
M4 C5 测试与压测 → C6 文档 → A 集成验收
```

B1 的模型没合，C4 的接口就 import 不到；C4 没合，C5 的接口测试跑不了。
**顺序错了不是能力问题，是流程问题**，卡住就在群里说，别自己硬写 mock 绕过。

## 四、日常同步（每天开工前 2 条命令）

```bash
git fetch origin
git rebase origin/main      # 把自己分支的基点挪到最新 main
```

为什么用 rebase 不用 merge：rebase 出来的历史是一条直线，`git log --graph` 一眼能看清谁在什么时候做了什么，答辩展示时也好看。

遇到冲突：

```bash
# 冲突文件会标出来
git status
# 手工改完，标记为已解决
git add <冲突文件>
git rebase --continue
# 想放弃重来
git rebase --abort
```

**冲突处理原则**：先看是谁的改动更新（`git log -1 --format=%ci <文件>`），保留更新的语义，不要机械选"我的"。

## 五、常见问题

**Q：能不能用 fork？**
A：不需要。同组一个仓库 + 每人一个分支就够了。fork 会让 `git fetch` 变复杂，还要多一层 upstream 同步。

**Q：我可以直接 push 到 main 吗？**
A：不能，main 开了保护。这是好事——它逼着每个人走 PR，留下评审记录。

**Q：我的分支落后太多，PR 冲突一堆怎么办？**
A：`git rebase origin/main` 后逐个解决。冲突超过 5 个文件，说明你分支活得太久，应该拆小、早点提 PR。

**Q：`dist/` 要不要提交？**
A：不要，已在 `.gitignore` 里。它是本地生成的分发包，随时可以用脚本重建。

**Q：怎么知道我的文件是不是都被别人改过？**
A：看 `.github/CODEOWNERS`。填完角色清单后，你负责的路径会自动把你加成评审人。

**Q：`push` 报 `RPC failed; curl 55 Send failure: Connection was reset`？**
A：八成是没走代理，见第七节。**这是 8 个人都会遇到的第一个坑**，先配好再动手。

## 六、给组长的检查清单

每次合并 PR 前，逐条对照：

- [ ] PR 只动了他自己包里的文件（`git diff --name-only` 自查过）
- [ ] CI 是绿的（`ruff check` + `pytest`）
- [ ] `python -m g05 preflight` 在他分支上通过
- [ ] 关联的 issue 有勾选完成项
- [ ] 没有偷偷改 `dto.py` / `config/*.yaml` / `models/base.py`
- [ ] 提交信息说清了"做了什么"，不是 "update" / "fix bug"

合并后立刻在 main 上跑一次全量：

```bash
git checkout main && git pull
python -m pytest -q
python -m g05 preflight
```

**绿了再合下一个**。main 一旦红了，所有人的 rebase 都跟着难受。

## 七、网络：推不上去先看这条（实测踩坑）

第一次推骨架时遇到的现象：

```
error: RPC failed; curl 55 Send failure: Connection was reset
send-pack: unexpected disconnect while reading sideband packet
fatal: the remote end hung up unexpectedly
```

`git ls-remote origin` 也会卡住两分钟以上不动。**这不是仓库权限问题，也不是凭据问题**，是直连 GitHub 不通。

原因：Git for Windows 用的 libcurl **不读 Windows 的"系统代理"设置**，浏览器能上不代表 git 能上。

### 修法（本机已有代理时）

```bash
# 先确认代理端口（Windows 设置 → 网络和 Internet → 代理，或看系统托盘里的代理软件）
# 本机实测是 127.0.0.1:7897

# 只给当前仓库配（推荐，不影响别的项目）
cd D:\G05            # 组员改成自己的仓库目录
git config http.proxy http://127.0.0.1:7897
git config https.proxy http://127.0.0.1:7897

# 顺手加上这两条，避免大仓库推送中途断流
git config http.version HTTP/1.1
git config http.postBuffer 524288000

# 验证：能秒回（空仓库无输出）就是通了
git ls-remote origin
```

配好之后 `git push` 从"卡 3 分钟然后报错"变成 5 秒完成。

### 想让所有项目都生效

```bash
git config --global http.proxy http://127.0.0.1:7897
git config --global https.proxy http://127.0.0.1:7897
```

### 以后代理关掉了，报 `Failed to connect to 127.0.0.1 port 7897`

把代理配置删掉即可：

```bash
git config --unset http.proxy
git config --unset https.proxy
```

### 判断到底是"网络"还是"权限"

| 现象 | 结论 |
|---|---|
| `git ls-remote origin` 卡住 / 超时 | 网络（配代理） |
| `ls-remote` 很快，但 `push` 报 403 | 权限（没被加成 Collaborator，或用了别人的账号） |
| 弹窗要求登录、登录后仍 403 | 账号不对，检查 Git Credential Manager 里存的是不是自己的账号 |
| `curl 55 Connection was reset` | 网络，且多半是 HTTPS 被重置 → 配代理，或改用 HTTP/1.1 |
